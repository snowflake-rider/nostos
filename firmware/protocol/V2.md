# NOSTOS v2 구현 계약

v2는 양쪽 펌웨어의 기본 개발 프로토콜입니다. ESP32가 실제 provisioned primary 주소를 등록된 source에
연결하지 못하거나 NVS session handshake를 완료하지 못하면 fail-closed로 송수신을 거부합니다. 배포에는
새 bundle release와 실물 검증이 필요합니다. API 기준은 `nostos_protocol.h`, UART는 `nostos_uart.h`,
상태·큐는 `nostos_state.h`, `nostos_bridge.h`, `nostos_endpoint.h`입니다.

## 공통 본문

```text
version:u8=2 | type:u8 | source:u8 | session:u32LE | sequence:u16LE | payload
```

헤더는 9B, 전체는 9~64B입니다. source는 1~3, session은 0이 아니어야 하며 모든 여러 바이트 정수는
Little-endian입니다. 길이는 외부 UART 프레임 또는 Mesh API가 제공합니다. encode/decode 오류 시 caller의
출력 버퍼·길이·구조체를 변경하지 않습니다.

| type | payload | 전체 |
| --- | --- | ---: |
| `10` BUTTON1/SPEED_DOWN | 없음 | 9B |
| `11` BUTTON2/SPEED_UP | 없음 | 9B |
| `13` BUTTON3/STOP | 없음 | 9B |
| `30` FALL | incident_session:u32LE, incident_id:u16LE | 15B |
| `41` ENVIRONMENT | temperature_code:u8, humidity_code:u8 | 11B |
| `42` FALL_CLEAR | incident_session:u32LE, incident_id:u16LE | 15B |
| `44` RIDE | valid:u8, kmh_x10:u16LE, distance_mm:u32LE | 16B |
| `50` HEARTBEAT | status:u8 | 10B |
| `51` ACK | acknowledged_source:u8, session:u32LE, sequence:u16LE, type:u8, result:u8 | 18B |

- application 공유 항목은 주행 속도·누적 바퀴 이동거리, 온도·습도, 버튼 1/2/3, 낙상 발생·해제뿐입니다.
  HEARTBEAT와 ACK는 내부 상태/제어용입니다. 등록표에 없는 type은 bridge가 전달하지 않습니다.
- incident session/id는 모두 0 금지입니다. RIDE valid는 0/1이며 invalid이면 kmh_x10과 distance_mm가
  모두 0이어야 합니다. distance_mm는 바퀴 회전으로 누적한 주행거리입니다.
- 온도 정상 code `0..250`은 `°C×10=code+225`, 습도 정상 code `0..200`은 `%×10=code×5`입니다.
  `251/252/253/254`는 범위 미만/초과/센서 오류/미측정이며 `255`와 습도 `201..250`은 거부합니다.
- HEARTBEAT bit0/1/2는 sensor/output/input-overflow 오류이고 상위 bit는 0이어야 합니다.
- ACK result `0/1/2/3`은 applied-or-queued/duplicate/unsupported/rejected입니다. ACK에 ACK하지 않으며
  자동 ACK·재전송·미결 요청 매칭은 구현하지 않았습니다. ACK는 출력 완료나 전달 보장이 아닙니다.

## UART 프레임

```text
7E | escaped(body_length:u8 | common_body | CRC16:u16LE) | 7E
```

`7E/7D`는 `7D` 뒤에 원래 값 XOR `20`으로 escape합니다. CRC-16/CCITT-FALSE는 poly `1021`, init
`FFFF`, refin/refout false, xorout `0000`이며 unescaped 길이+본문을 검사합니다(`123456789 → 29B1`).
본문 최대 64B, 최악 프레임 136B이고 고정 버퍼만 사용합니다. 바이트 간격이 100ms를 초과하거나
길이·escape·CRC가 틀리면 다음 `7E`까지 버립니다. CRC는 인증이 아닙니다.

### ESP32 로컬 센서 프레임

ESP32에 직접 연결된 BLE 센서 측정은 공식 NOSTOS 발신자가 되기 전에 STM32의 공통 센서 저장소로
전달합니다. 이 프레임은 UART1에서만 쓰며 Mesh payload가 아닙니다.

```text
A5 5A | version=01 | type:u8 | length:u8 | payload | CRC16:u16LE
```

| type | payload | 전체 |
| --- | --- | ---: |
| `02` HELLO | 없음 | 7B |
| `03` IDENTITY | source_id:u8, session_id:u32LE | 12B |
| `04` APPROVE_SESSION | source_id:u8, session_id:u32LE, sequence_floor:u16LE | 14B |
| `05` IDENTITY_ACK | source_id:u8, session_id:u32LE | 12B |
| `06` RIDE | valid:u8, kmh_x10:u16LE, distance_mm:u32LE | 14B |

CRC-16/CCITT-FALSE는 `version`부터 payload까지 검사합니다. source_id는 1~3이고 session_id는 0이
아니어야 합니다. RIDE valid가 0이면 속도와 누적거리 모두 0이어야 합니다. parser는 최대 14B 고정
버퍼로 length를 따라 수신하고 바이트 간격이 100ms를 초과하거나 길이·CRC·값이 틀리면 다음
preamble에서 재동기화합니다. IDENTITY_ACK는 STM32가 정확한 IDENTITY source/session을 확인했음을
응답하므로 ESP32가 확인되지 않은 새 session을 반복 생성하지 않습니다.

STM32가 RIDE를 수신·저장한 뒤 자신의 source/session/sequence로 공식 `NOSTOS_RIDE`를 생성합니다.
따라서 ESP32 BLE producer와 STM32가 같은 센서값을 각각 Mesh에 발행하지 않습니다.

## 수신·상태·큐·출력 스케줄링 제약

- ESP32는 provisioned 원 발신 Mesh 주소와 payload source를 사전 등록된 1~3 매핑으로 검증합니다.
  등록표에 없는 type과 제거된 type은 `UNSUPPORTED_TYPE`으로 거부하고 큐에 넣지 않습니다.
- 원격 NOSTOS packet은 자신의 세션을 승인할 수 없습니다. ESP32가 검증한 Mesh 원 발신 주소와 본문
  source를 대조한 뒤, 같은 UART의 `APPROVE_SESSION`과 공식 packet을 단일 writer가 연속 전달합니다.
  STM32는 같은/낮은 승인 세션과 승인 floor 미만 sequence를 거부하고 floor 자체는 수락합니다. 더 높은
  session 승인은 해당 source의 `shared_data`, pending STOP/버튼, FALL 사건과 닫힌 tombstone을 모두 비운
  strict empty epoch를 시작합니다. 다른 source의 상태와 replay window는 그대로 보존합니다.
- source별 64순번 창이 중복·오래된 순번을 거부합니다. sequence 65535 다음은 `EXHAUSTED`이며 wrap하지 않습니다.
- FALL/FALL_CLEAR는 source+incident session/id로 식별합니다. 사건/tombstone은 고정 24칸이고
  같은 source session 안에서는 자동 만료·eviction하지 않습니다. CLEAR 선도착과 정확한 사건별 mute를
  보존하지만 더 높은 source session은 이전 epoch의 FALL/tombstone을 명시적으로 폐기합니다. 이는 source
  reset을 이전 process lifetime의 종료로 간주하는 제품 선택입니다. 따라서 reset 뒤 새 session이 승인되면
  이전 FALL은 별도 FALL_CLEAR 없이 끝나며, 재부팅 이후에도 위험이 계속되면 새 session에서 FALL을 다시
  감지·발행해야 합니다.
- RIDE와 ENVIRONMENT는 source별 독립 ordering을 적용하고 센서 freshness는 로컬 수신 기준 3000ms입니다.
  수락한 최신 센서값은 application `shared_data`의 해당 source 항목을 덮어쓰며 별도 이력 큐에 쌓지
  않습니다. invalid RIDE 보고는 마지막 정상 속도·누적거리와 그 시각을 덮지 않습니다.
- 출력 상태는 FALL 활성 여부만 반영합니다. 활성 FALL은 빨간 점멸과 긴급 부저이며 정확한 사건 mute는
  빨간 표시를 유지하고 부저만 끕니다. FALL_CLEAR 뒤에는 둘 다 꺼집니다.
- ESP32 bridge는 16칸 중 4칸을 FALL/FALL_CLEAR 긴급용으로 예약하고 4개 긴급 후 일반 1개를 처리하며
  최대 대기는 2000ms입니다. 이 bridge 큐와 STM32 UART ISR 수신 ring은 비동기 UART/Mesh 경계를
  보호하므로 그대로 유지합니다. 실패·부분 UART 송신은 자동 재시도하지 않습니다.
- ESP32가 새 STM32 부팅의 첫 `HELLO`를 받으면 이전 process lifetime의 bridge/control/deferred RIDE와
  XOSS notification 큐, 속도 baseline·session distance를 먼저 비우고 새 identity session을 NVS에
  commit합니다. 같은 부팅의 반복 `HELLO`는 큐를 다시 비우거나 session을 다시 증가시키지 않고 동일
  identity만 재전송합니다. 초기화나 NVS commit이 실패하면 일반 UART/Mesh/RIDE 경로는 닫힌 채 다음
  `HELLO` 재시도만 허용합니다. 이 경계는 BLE 연결과 Mesh provisioning·key를 지우지 않으며, replay
  방지를 위한 NVS identity session 번호도 0으로 초기화하지 않습니다.
- STM32 application/output scheduler는 기존 8칸/2000ms 버튼 요청 큐를 사용하지 않습니다. 고정
  `pending_stop[1]`과 `pending_button[1]`만 두며 시간 기반 만료가 없습니다. FALL/FALL_CLEAR는 이 슬롯에
  넣지 않고 incident 상태 처리에서 즉시 안전상태 latch를 갱신합니다.
- 출력 처리 우선순위는 `FALL 안전상태 > BUTTON3/STOP > BUTTON1·BUTTON2`입니다. 유효한 FALL로
  안전상태가 활성화되는 즉시 두 pending 슬롯을 비우고 재생 중인 일반 오디오를 선점합니다. STOP은
  pending BUTTON1·BUTTON2를 비우고 해당 버튼 오디오를 선점합니다. 오디오 처리 중 도착한
  BUTTON1·BUTTON2는 의도적으로 버리며 나중에 재생하지 않습니다.
- 위 단순화는 STM32 application/output scheduler 내부 정책만 바꿉니다. wire framing과 session 승인,
  source/sequence 중복 제거, incident/tombstone, ESP32 bridge 12개 일반+4개 긴급 슬롯 계약은 변경하지
  않습니다.
- 공통 코드는 동적 할당·lock·Mesh TTL/암호화/재조립을 수행하지 않습니다. caller가 직렬화하고 Mesh
  스택이 TTL7과 보안을 담당하며 수신 callback에서 응용 재방송하지 않습니다.

## 활성화 경계

- ESP32: `CONFIG_NOSTOS_PROTOCOL_V2=y`, source1~3의 실제 Mesh primary 주소를 설정합니다. provisioned
  primary로 local source를 자동 선택하고 session을 NVS에 먼저 증가·commit한 뒤 IDENTITY를 보냅니다.
  STM32 HELLO 하나당 한 번만 증가하며 정확한 IDENTITY_ACK 전까지 같은 session을 재전송합니다.
  주소 0/중복/불일치는 송수신을 거부합니다. opcode는 vendor `0x21/0x02E5`, UART1은 TX17/RX18,
  115200/8N1입니다.
- STM32: CMake `-DNOSTOS_PROTOCOL_V2=ON`. boot는 UART를 준비하고 HELLO를 주기적으로 보내며, ESP32의
  유효한 IDENTITY가 도착한 뒤 그 source/session으로 endpoint를 자동 초기화하고 IDENTITY_ACK를 보냅니다.
  그 전의 공식 NOSTOS 송수신은 `NOSTOS_NOT_READY`입니다. peer session은 ESP32의 주소 검증 뒤 전달된
  APPROVE_SESSION으로 승인합니다. 준비 전 raw v1 fallback이나 자동 Flash는 하지 않습니다.

새 type은 등록표·고정 길이·codec·상태 처리·golden fixture를 함께 추가합니다. 기존 `(version,type)`의
길이·의미를 바꾸지 말고 헤더 의미가 바뀌면 새 version을 사용합니다.

## 검사

```sh
bash firmware/tools/fw check protocol
bash firmware/tools/fw test protocol
```

CMake는 v2 라이브러리를 strict/sanitizer로 컴파일하고 codec·UART·상태·안전 로직 CTest를 실행합니다.
v2 동작 변경은 양쪽 타깃 빌드와 실물 검증까지 통과해야 배포할 수 있습니다.
