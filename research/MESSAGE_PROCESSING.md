# NOSTOS 메시지 처리 규칙

이 문서는 버튼, 센서, FALL/SOS 메시지를 같은 기준으로 처리하기 위한 설계 규칙입니다.
아직 펌웨어와 실물 장비에서 구현·검증한 결과는 아닙니다.

관련 테스트 사례: [CASES.md](CASES.md)

## 처리 흐름

```text
메시지 수신
→ 형식과 출처 검사
→ 중복 검사
→ 우선순위와 충돌 판단
→ 큐 저장
→ LED·MP3·버저 또는 센서 상태 처리
→ 결과 기록
```

- STM32는 버튼·센서·낙상을 판단하고 LED, MP3, 버저를 제어합니다.
- ESP32는 UART와 Bluetooth Mesh 사이에서 메시지를 전달합니다.
- ISR과 통신 callback은 메시지를 큐에 넣기만 합니다.
- 실제 판단과 출력은 worker 또는 STM32 메인 루프에서 실행합니다.

## 우선순위

숫자가 작을수록 먼저 처리합니다. 같은 우선순위에서는 먼저 받은 메시지를 먼저 처리합니다.

| 우선순위 | 메시지 | 기본 동작 |
| --- | --- | --- |
| P1 | FALL, SOS | 다른 MP3를 중단하고 `emergency.mp3` 재생, 버저 작동 |
| P1 | FALL_CLEAR, SOS_CLEAR | 해당 사건 종료, 버저 중단 |
| P2 | 버튼 3 STOP | 버튼 1·2 MP3를 중단하고 `stop_request.mp3` 재생 |
| P3 | 버튼 2 Pace Down | `speed_down_request.mp3` 재생 |
| P4 | 버튼 1 Pace Up | `speed_up_request.mp3` 재생 |
| 출력 없음 | 센서, HEARTBEAT | 최신 상태만 갱신 |

## 버튼 충돌 규칙

버튼 1·2는 바로 재생하지 않고 처음 요청부터 `300ms` 동안 모아서 판단합니다.
`300ms`는 시작값이며 실물 Mesh 측정 후 조정합니다.

| 같은 판단 시간에 받은 요청 | 결과 |
| --- | --- |
| 버튼 1만 있음 | Pace Up 한 번 실행 |
| 버튼 2만 있음 | Pace Down 한 번 실행 |
| 같은 버튼을 여러 노드가 누름 | 같은 동작을 한 번만 실행 |
| 버튼 1과 버튼 2가 함께 들어옴 | 안전을 위해 버튼 2가 승리 |
| 버튼 3이 들어옴 | 대기 중인 버튼 1·2를 버리고 STOP 즉시 실행 |
| FALL/SOS가 들어옴 | 대기 중인 일반 버튼을 버리고 비상 동작 즉시 실행 |

로컬 버튼도 같은 판단 큐를 사용합니다. 그래야 송신 노드와 수신 노드가 같은 결과를 내기 쉽습니다.

예시:

```text
A → 버튼 1
B → 곧바로 버튼 2
결과 → 버튼 2 승리 → speed_down_request.mp3 한 번 재생
```

## MP3와 버저 규칙

- 버저는 음소거되지 않은 FALL/SOS 사건이 있을 때만 울립니다.
- `emergency.mp3`는 같은 사건에서 한 번만 재생합니다.
- 버저는 FALL_CLEAR, SOS_CLEAR 또는 로컬 버튼 4 음소거까지 계속 울립니다.
- 버튼 4 음소거는 소리만 끄며 사건 자체를 종료하지 않습니다.
- P1은 재생 중인 모든 낮은 우선순위 MP3를 중단합니다.
- P2는 버튼 1·2 MP3를 중단하지만 P1을 중단하지 못합니다.
- 높은 우선순위 때문에 밀린 버튼 MP3는 나중에 다시 재생하지 않습니다.
- 중복 메시지는 MP3와 버저를 다시 시작하지 않습니다.
- 센서와 HEARTBEAT은 MP3와 버저를 사용하지 않습니다.

## 메시지 검사 규칙

- 버전, 길이, CRC, 종류, 출처를 검사합니다.
- 승인된 session과 source별 sequence를 확인합니다.
- 같은 `source + session + sequence`는 한 번만 처리합니다.
- 잘못된 메시지는 출력하지 않고 거부 결과를 기록합니다.
- 오류 메시지 다음에 들어온 정상 메시지는 계속 처리합니다.
- 전송 성공, 수신 성공, 실제 출력 성공은 서로 따로 기록합니다.
