## Problem Statement

The submission deck already contains a generic five-step firmware flow on slide 07, but it does not show how one rider's input becomes another rider's accepted application event and physical-facing output. A second generic component diagram would repeat the existing story without increasing evaluator understanding.

## What Makes This Cool

One diagram connects product behavior to the real firmware seams: sensor/button/fall input, STM32 services, the shared protocol and CRC16 UART frame, ESP32 priority/latest-state handling, Bluetooth Mesh, the peer STM32 application, and OLED/RGB/audio/buzzer output. The return `STOP_ACK` makes the important distinction visible: bytes sent or Mesh API acceptance are not the same as peer STM32 application acceptance.

## Constraints

- Keep the deck at 20 pages by replacing the body of current slide 07 rather than adding a duplicate architecture page.
- Match the existing white, navy, cyan, light-gray, and coral visual system.
- Preserve one claim, one supporting sentence, one main diagram, and one evidence footer.
- Limit visible code identifiers to `message_protocol_service`, `nostos_protocol/nostos_uart`, and `bridge_runtime`.
- Do not claim three-node physical end-to-end success. Host logic and target build evidence remain separate from physical E2E verification.
- Use color plus line style and arrow labels so the three traffic classes remain distinguishable under projection and color-vision differences.
- Use a 16:9 layout with body labels at least 18 pt, footer labels at least 12 pt, and no connector crossing card text.
- Keep implementation identifiers as supporting labels, not the visual headline.

## Premises

1. The slide must explain an event-to-action path across two rider nodes, not enumerate every source file.
2. Normal state and safety traffic share the system but have different runtime policies and therefore need separate visual paths.
3. `STATE_UPDATE` uses latest-state behavior, while `STOP_REQUEST` and `STOP_ACK` use priority queues and explicit acceptance semantics.
4. The receiving STM32 application is the acceptance boundary for `STOP_ACK`.
5. Existing slide 07 is the correct replacement target because it already owns the architecture narrative role.
6. `STOP_ACK` is generated only after Rider B's STM32 application accepts `STOP_REQUEST`; UART receipt, CRC validation, ESP32 receipt, Mesh receipt, or Mesh API acceptance must not generate it.

## Approaches Considered

### Approach A: Dual-plane End-to-End Architecture

Two mirrored Rider Node stacks surround Bluetooth Mesh. Cyan `STATE_UPDATE`, coral `STOP_REQUEST`, and navy return `STOP_ACK` paths connect the stacks. This approach was selected because it links normal telemetry, the SSD1306 dashboard, safety priority, and application acceptance in one system view.

### Approach B: STOP-only Transaction

Show only fall/button STOP, peer output, and ACK return. Rejected because it removes the sensor-to-dashboard relationship and narrows the page to one feature.

### Approach C: Code Module Stack

Show `app.c → message_protocol_service.c → nostos_protocol/nostos_uart → bridge_runtime.c`. Rejected because it overlaps the existing slide 07 and prioritizes filenames over evaluator understanding.

## Recommended Approach

Replace slide 07's current five-stage pipeline with two capability-identical node stacks and one highlighted exemplar transaction. Each node contains `Device I/O (Inputs + Outputs)`, `STM32 Services`, `Protocol + CRC16/UART`, and `ESP32 Bridge`; the current example assigns Rider A the source role and Rider B the receiver role, but the roles are reversible.

```text
Rider Node A (example source)          Bluetooth Mesh          Rider Node B (example receiver)
Device I/O: Inputs + Outputs                                    Device I/O: Inputs + Outputs
             ↕                                                               ↕
STM32 Services ↔ Protocol + CRC16/UART                Protocol + CRC16/UART ↔ STM32 Services
             ↕                                                               ↕
ESP32 Bridge  ⇄───────────────────────── Mesh ─────────────────────────────⇄  ESP32 Bridge

STATE_UPDATE  ·······················································▶  B bridge_runtime: latest-state
STOP_REQUEST  ═══════════════════════════════════════════════════════════▶  B bridge_runtime: priority
                                                                         B STM32 application ACCEPT
                                                                         → STOP_ACK created
                                                                         → B ESP32 priority queue
STOP_ACK      ◀──────────────────────────────────────────────────────────  Mesh return
```

Visual hierarchy:

1. Title: `한 라이더의 입력을 다른 라이더의 행동으로 연결합니다`
2. Subtitle: `정상 상태는 최신값으로, 긴급 STOP은 우선 처리와 application ACK로 전달합니다`
3. Main structure: two identical-capability Rider Nodes around Bluetooth Mesh, with A-as-source and B-as-receiver highlighted as an example
4. Message paths: cyan dotted state, coral thick STOP, navy solid ACK return; every lane keeps its message label
5. Acceptance gate: `STOP_REQUEST received → application accepts → STOP_ACK created` inside Rider B's STM32 layer
6. Footer: `검증됨: host logic, target build · 미검증: 3-node physical E2E`

Message lanes must occupy dedicated space between the node stacks rather than crossing card text. The text specification above is authoritative; the temporary workshop sketch is not a handoff dependency.

## Success Criteria

- An evaluator can identify both rider nodes, the Mesh boundary, and the receiving output within 10 seconds.
- `STATE_UPDATE`, `STOP_REQUEST`, and return `STOP_ACK` are visually distinct without a legend lookup.
- The slide shows that Rider B STM32 application acceptance creates `STOP_ACK`; no transport-layer receipt or API acceptance appears as the ACK source.
- The slide does not imply that three-node physical E2E verification is complete.
- The architecture slide is readable at normal presentation zoom and does not duplicate the current slide 07 pipeline.
- The deck remains 20 pages and keeps the surrounding slide order intact.
- Both node cards expose the same input, output, STM32, protocol/UART, and ESP32 capabilities while the highlighted example remains A request → B action → A acknowledgement.
- A full-slide 16:9 export at 100% keeps body labels at 18 pt or larger, footer labels at 12 pt or larger, and all connectors clear of text.
