## Problem Statement

현재 20페이지 Google Slides는 NOSTOS의 실제 펌웨어 구조와 검증 경계를 대체로 정확하게 설명하지만, 공식 개발완료보고서 목차와 페이지 배분이 명시적으로 드러나지 않는다. 개발 개요에서 입력→STM32→UART→ESP32 흐름이 반복되고, 프로그램 설명과 차별성에서 STOP/ACK 및 낙상 로직이 재등장하며, 일부 페이지에는 겹침·잘림·과도한 소형 텍스트가 있다.

따라서 총 20페이지를 유지하면서 다음 공식 배분에 맞춰 이야기의 역할을 재정의한다.

- 개발 개요: 3P
- 개발 환경 설명 + 개발 프로그램 설명 + 장애 요인과 해결 방안: 합계 10P
- 결과물의 차별성 + 파급력 및 기대 효과: 합계 5P
- 개발 일정 및 업무 분장: 2P

## What Makes This Cool

이 발표의 가장 강한 장면은 단순한 부품 목록이 아니라, 한 라이더의 입력이 로컬 STM32 서비스와 공통 protocol/UART, ESP32-S3 Bluetooth Mesh를 거쳐 다른 라이더의 OLED·RGB·오디오·부저 행동으로 바뀌는 과정이다. 여기에 정상 상태는 latest-state로, 긴급 STOP은 priority queue와 STM32 application acceptance 기반 ACK로 처리한다는 차이가 결합된다. SSD1306 dashboard는 이 내부 구조가 사용자가 즉시 이해할 수 있는 주행 정보로 변환된 결과를 보여주는 시각적 증거다.

## Constraints

- 표지를 포함해 정확히 20페이지를 유지한다.
- 공식 목차의 페이지 합계 `3 + 10 + 5 + 2 = 20`을 지킨다.
- 개발 개요 3P 안에 소스코드와 시연 동영상의 실제 클릭 가능한 링크를 넣는다.
- 현재 Google Slides의 `C08`(화면 표기 07) end-to-end architecture와 `C10`(화면 표기 09) SSD1306 dashboard를 새 `N07`, `N09`의 핵심 anchor로 보존한다.
- `STATE_UPDATE`, `PACE_REQUEST`, `STOP_REQUEST`, `STOP_ACK`의 네 메시지와 ACK 의미를 현재 코드보다 과장하지 않는다.
- `STOP_ACK`는 상대 STM32 application acceptance를 의미하며, Mesh API 성공·UART 수신·물리 출력 완료와 동일시하지 않는다.
- host check, target build, 실제 센서·RF·출력의 3-node physical E2E를 서로 다른 증거 단계로 표시한다.
- 현재 미확인인 physical 3-node STOP E2E를 완료로 주장하지 않는다.
- 16:9 Google Slides를 authoritative artifact로 유지한다.
- 이번 design 단계에서는 Google Slides를 편집하지 않는다. 승인 후 별도 구현 단계에서 수정한다.

## Premises

1. 심사위원은 파일 수보다 입력이 어떤 application behavior로 이어지는지 먼저 이해해야 한다.
2. 공식 목차는 별도 divider를 추가하지 않고, `SECTION 03 · 개발 프로그램 설명` 형식의 고정 eyebrow와 페이지 역할로 드러낸다.
3. 20페이지를 지키기 위해 기존 개발 개요의 02·03페이지 내용을 한 장으로 병합하고, 확보한 한 장을 기대 효과의 발전 로드맵에 사용한다.
4. 개발 환경·프로그램·장애 대응 10P는 각각 3P·5P·2P로 배분한다.
5. 차별성·파급력 5P는 각각 3P·2P로 배분한다.
6. 동일한 기술이 다시 등장할 때는 반복 설명이 아니라 다른 질문에 답해야 한다. 예를 들어 낙상 알고리즘은 판정 흐름, calibration은 차별화된 기준 설정을 설명한다.
7. cyan은 정상 데이터와 일반 강조, coral은 STOP·FALL 같은 안전 의미, navy는 구조와 ACK 의미에 사용한다.

## Approaches Considered

- A — 최소 수정형: 겹침·잘림과 명백한 오류만 고치는 방식. 공식 목차의 서사와 반복 문제를 충분히 해결하지 못해 선택하지 않았다.
- B — 심사위원 중심 20P 재설계: 페이지 수와 검증된 내용을 유지하면서 각 페이지의 역할을 공식 목차에 재배치한다. 사용자가 선택했다.
- C — 14~16P Judges' Cut: 발표 전달력은 높지만 별도 deck 관리와 제출 페이지 규정 위험이 있어 현재 authoritative deck에는 적용하지 않는다.

## Non-goals

- 펌웨어 코드·protocol·queue 정책은 변경하지 않는다.
- 새로운 hardware test나 physical E2E 증거를 이 발표 작업 안에서 만들지 않는다.
- 근거가 없는 시장 규모·판매 수치·성능 수치를 추가하지 않는다.
- 14~16P Judges' Cut이나 별도 발표 deck을 만들지 않는다.
- PPTX 재생성·동기화는 이번 작업 범위에서 제외하며, 사용자가 별도로 요청할 때만 export와 QA를 수행한다.

Layout 규격은 공통적으로 전체 canvas 상단 15%에 eyebrow+headline, 하단 8%에 evidence footer, 우하단에 page number를 둔다. `L1–L6`의 비율은 이를 제외한 77% content region 기준이며, `L3`의 좌측 60% main visual+우측 32% explanation 사이 나머지 8%는 gutter다. `L1`은 중앙 hero, `L2-H`는 좌→우 단일 흐름, `L3`는 split view, `L4`는 양쪽 3-layer node tower와 중앙 Mesh/message lane을 사용하며 file identifier는 supporting label로 둔다. `L5`는 STM32 A/ESP A/Mesh/ESP B/STM32 B의 5개 lane, `L6`는 2~4행 비교 matrix다.

본문 예산은 headline 1~2행, supporting bullet 최대 3개×2행, diagram node 최대 6개, evidence footer 1행이다. 예외적으로 N09는 OLED mockup 내부 최대 8행, N16은 비교 항목 최대 4행, N20은 확정 팀원 수만큼 최대 5행을 허용한다.

### 시각 시스템

- Canvas: white 또는 off-white `#F8FAFC`.
- Primary ink: navy `#071A2B`; 일반 본문에 pure black을 사용하지 않는다.
- Data accent: cyan `#55C1E7`; 정상 상태, 데이터 흐름, 일반 강조에 사용한다.
- Safety accent: coral `#FF6B6B`; STOP_REQUEST, FALL, 위험과 미검증 경계에만 사용한다. STOP_ACK 경로와 설명은 navy를 사용하고, request와 한 쌍임을 보일 때만 작은 coral outline marker를 붙인다.
- Secondary text: gray `#5B6472`; 보조 설명과 caption에 사용한다.
- Typography: Google Slides import/export probe 결과 본문은 `Arial`을 사용하고 Korean glyph는 Google의 `Gulim`/`BatangChe` fallback으로 export한다. 실제 PDF visual QA에서 깨짐이 없음을 확인한 이 조합을 이번 deck의 승인 fallback으로 고정한다. 코드 identifier는 `Roboto Mono`를 사용한다.
- Title 30–34 pt, subtitle 19–21 pt, body 17–19 pt, caption/evidence footer 12–14 pt를 기준으로 한다.
- 한 페이지에는 하나의 주장, 최대 세 개의 시각 영역만 둔다. 동일 크기 3-card는 세 항목의 동등 비교가 실제 의미일 때만 사용한다.
- page number는 우하단 safe area 안에 완전한 두 자리 숫자로 표시한다. `11·13·15·17·19`의 leading digit clipping을 제거한다.
- connector는 텍스트 박스를 가로지르지 않는다. 메시지 방향은 화살표와 label을 모두 사용해 색상 없이도 구별 가능하게 한다.

### Design Review Decisions

- N07은 message lane 우선 구조를 사용한다. Node tower는 `Device I/O → STM32 Services → ESP32 Bridge` 세 덩어리로 단순화하고, `nostos_protocol · CRC16/UART`는 STM32↔ESP32 seam label로 표시한다. `STATE_UPDATE`, `STOP_REQUEST`, `STOP_ACK`는 중앙 전용 band에 두며 layer text를 가로지르지 않는다. 상세 transaction 단계는 N11만 담당한다.
- N09는 실제 SSD1306의 128×64 비율을 반영한 2:1 OLED hero를 왼쪽 65%에 두고, 오른쪽 30%에는 `FALL → Calibration → Dashboard` 우선순위만 둔다. 하단 여백은 장식으로 채우지 않으며 footer와 OLED frame을 분리한다.
- N11은 별도 green event lane을 만들지 않는다. Coral STOP line이 peer STM32 acceptance gate로 들어가고, navy ACK line이 그 gate에서 되돌아오는 두 방향만 보여준다. Acceptance gate 내부에는 `received → application accepts → ACK created` 세 단계만 둔다.

### 증거 표기 규칙

- source inspection으로 확인된 내용: `CODE VERIFIED`.
- host/static check를 실제 실행해 확인한 내용: `HOST CHECK VERIFIED`.
- target configure/build까지 확인된 내용: `TARGET BUILD VERIFIED`.
- 개별 실제 보드·센서·출력에서 확인된 내용: `PHYSICAL COMPONENT VERIFIED`.
- 완전한 실제 node 간 경로에서 확인된 내용: `PHYSICAL E2E VERIFIED`; 아직 확인하지 않은 3-node STOP 경로는 `PHYSICAL E2E PENDING`.
- `Verification` 허용 token: `CODE VERIFIED`, `HOST CHECK VERIFIED`, `TARGET BUILD VERIFIED`, `PHYSICAL COMPONENT VERIFIED`, `PHYSICAL E2E VERIFIED`, `PHYSICAL E2E PENDING`, `NOT RUN`.
- `Status` 허용 token: `MEASURED`, `HYPOTHESIS`, `EXPECTED USE`, `ROADMAP`, `RIDE TUNING PENDING`.
- `Provenance` 허용 token: `CURRENT CODE`, `CURRENT DECK`, `TEAM RETROSPECTIVE`, `USER CONFIRMED`.
- footer는 `Verification: … | Status: … | Provenance: …` 순서를 사용하고 해당 범주가 없으면 생략한다. 팀 회고에서 나온 기간·조달 판단과 현재 코드 동작을 같은 범주로 합치지 않는다.
