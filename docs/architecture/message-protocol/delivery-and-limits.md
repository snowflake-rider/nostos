# 전달·재생 조건과 검증 한계

[목차](README.md) · [전체 흐름 그림](02-one-message.md)

## 보냈다는 로그와 받았다는 로그

`MESH_TX ... api=accepted`는 **송신 장치의 API가 요청을 받아들였다**는 뜻입니다.

상대 ESP32의 수신은 상대의 `MESH_RX` 등으로 확인합니다. 상대 STM32의 수신과 스피커의 실제 소리도 각각 확인해야 합니다.

현재 앱에는 **수신 확인 응답이나 실패 시 자동 재시도가 없습니다.** 언제나 전달된다고 생각하면 안 됩니다.

## 전체 그림에서 생략한 것

- **A의 로컬 알림:** A도 정지 요청을 만들 때 자기 알림을 처리합니다.
- **네트워크 설정:** 양쪽의 Mesh 키·그룹 등 설정이 맞아야 합니다. 그룹 수신자 중 B 한 대만 그렸습니다.
- **중계:** 중간 Relay 노드는 생략했습니다. 그림만으로 다중 홉 전달이 검증된 것은 아닙니다.
- **대기·실패:** 큐 대기와 실패 경로는 그림에서 생략했습니다.
- **오디오 조건:** 초기화·연결이 정상이어야 합니다. 현재 다른 음원이 재생 중이면 새 재생 요청은 무시합니다.
- **출력 종류:** 정지 요청은 음성 재생 대상입니다. LED·부저나 브레이크를 작동시키는 명령이 아닙니다.

## 어디까지 확인했나?

이 스터디 노트는 현재 코드를 설명합니다. **문서를 작성하면서 새 실물 시험을 하지는 않았습니다.**

기존 결과와 남은 검증은 [검증 안내](../../verification/index.md)에서 확인하세요.

## 이번 입문에서 다루지 않은 것

큐, 그룹 주소, Relay, 센서별 판정의 세부 구현은 [상세 참고](reference.md)로 남겼습니다. 현재 이벤트 형식에는 문장이나 거리·속도 측정값도 들어 있지 않습니다.
