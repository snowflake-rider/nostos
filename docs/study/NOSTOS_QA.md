# NOSTOS 발표 Q&A 노트

교수님·프로젝트 발표 질의응답을 위한 짧은 답변 모음이다. 먼저 **한 줄 답변**으로 결론을 말하고,
추가 질문이 들어오면 아래 설명을 덧붙인다.

## 30초 프로젝트 소개

NOSTOS는 현재 세 대, 최대 열 대의 라이더 노드가 주행·환경 상태와 Pace Up, Pace Down, STOP 요청을
공유하는 자전거 그룹 라이딩 시스템입니다. 각 노드는 STM32가 센서·버튼·화면·출력을 담당하고,
ESP32-S3가 UART와 Bluetooth Mesh 사이의 통신을 중계합니다. 현재 공통 프로토콜과 장치별 기반은
구현 중이며, 다중 노드 relay와 모든 센서를 포함한 실물 종단 간 검증은 별도로 필요합니다.

## 핵심 Q&A

### Q1. NOSTOS가 해결하려는 문제는 무엇인가요?

**한 줄 답변:** 라이더가 주행 중에도 뒤를 돌아보거나 휴대전화를 조작하지 않고 그룹 상태와 주행
신호를 공유하게 하는 것이 목표입니다.

노드는 주행 상태와 환경 상태를 항상 수신합니다. 버튼 1, 2, 3으로 각각 Pace Up, Pace Down, STOP을
요청하고, 수신 노드는 OLED, LED, 오디오 같은 출력으로 이를 알려 줍니다. 낙상을 감지해도 STOP 요청과
같은 흐름을 사용합니다.

### Q2. 시스템은 어떻게 구성되어 있나요?

**한 줄 답변:** 현재 Rider Node 1, 2, 3이 있으며, 설계상 최대 10개까지 늘릴 수 있고 각 노드는 STM32와 ESP32-S3를 한 쌍으로 사용합니다.

- Rider Node 1의 현재 capability: XOSS 속도 센서
- Rider Node 2의 현재 capability: DHT11 온습도 센서
- Rider Node 3의 현재 capability: MPU6050 움직임 센서
- 공통 장치: SSD1306, VS1003B, 버튼, RGB LED, 부저

Rider Node ID는 사람이나 선두·중간·후미 위치가 아니라 장비 식별자입니다. 라이더가 위치를 바꿔도 Node ID는
그대로이며, ESP32의 provisioned Mesh 주소와 Node ID binding으로 발신자를 검증합니다.

### Q3. STM32와 ESP32를 함께 사용하는 이유는 무엇인가요?

**한 줄 답변:** 로컬 장치 제어와 무선 통신의 책임을 분리하기 위해서입니다.

STM32는 센서값, 버튼 입력, 화면과 오디오 같은 애플리케이션 상태를 관리합니다. ESP32-S3는
Bluetooth Mesh와 UART bridge를 담당합니다. 이 구조는 무선 기능이 바뀌어도 STM32의 장치 제어
코드를 비교적 독립적으로 유지할 수 있다는 장점이 있습니다.

### Q4. 버튼을 누른 뒤 다른 노드에 전달되는 과정은 어떻게 되나요?

**한 줄 답변:** `버튼 → STM32 → UART → ESP32 → Bluetooth Mesh → 상대 ESP32 → UART → 상대 STM32`
순서로 전달됩니다.

상대 STM32는 메시지를 적용한 뒤 OLED, LED, 오디오 같은 로컬 출력을 갱신합니다. 단, 전송 함수의
성공은 상대 노드가 실제로 출력까지 완료했다는 뜻은 아닙니다.

### Q5. Bluetooth Mesh를 선택한 이유는 무엇인가요?

**한 줄 답변:** 여러 라이더 노드가 같은 네트워크에 참여하고, 직접 닿지 않는 노드의 메시지도 relay할
수 있는 구조가 필요하기 때문입니다.

일반적인 일대일 BLE 연결보다 다수 노드 확장에 적합합니다. relay를 활성화하더라도 실제 거리와 장애물
조건에서 여러 노드를 거친 전달은 별도의 실물 시험으로 확인해야 합니다.

### Q6. UART와 Mesh에서 같은 데이터를 그대로 보내나요?

**한 줄 답변:** 공통 메시지의 의미는 공유하지만, 전송 매체에 맞는 포장 방식은 다릅니다.

애플리케이션 본문은 `type + source_node_id + payload` 형식입니다. Mesh에는 이 본문을 보내고, UART에서는
`A5 5A + length + 본문 + CRC16`으로 감쌉니다. UART의 CRC는 유선 전송 오류를 검출하기 위한 것입니다.

### Q7. 왜 v1과 v2를 함께 유지하지 않나요?

**한 줄 답변:** 두 실행 경로를 동시에 유지하면 시험 조합과 장애 원인이 불필요하게 늘어나므로 하나로 합쳤습니다.

현재 메시지는 `STATE_UPDATE`, `PACE_REQUEST`, `STOP_REQUEST`, `STOP_ACK` 네 종류뿐입니다. 복잡했던 boot
session과 전역 sequence는 제거했습니다. Mesh 요청 ID는 ESP32가 무작위로 만들고 STM32 local STOP은
boot-local counter를 사용합니다.

### Q8. CRC를 사용하는 이유는 무엇인가요?

**한 줄 답변:** UART 전송 중 데이터가 손상되었는지 검출하기 위해 사용합니다.

UART frame은 CRC-16/CCITT-FALSE를 사용하고, 길이·CRC가 잘못된 프레임을 버립니다. CRC는 우연한
전송 오류를 찾는 장치이지 인증이나 암호화 수단은 아닙니다.

### Q9. 중복되거나 순서가 뒤바뀐 메시지는 어떻게 처리하나요?

**한 줄 답변:** 상태는 최신 값으로 덮어쓰고, 요청은 최근 `request_id`를 RAM에서 기억해 재처리를 막습니다.

재부팅하면 이 임시 기록과 상태 cache를 모두 비웁니다. 오래된 요청을 영구 저장하지 않으며, ESP32는
실제 Mesh 발신 주소와 payload의 source가 일치하는지 확인합니다.

### Q10. STOP은 어떻게 확인하나요?

**한 줄 답변:** 먼저 그룹 주소로 알리고, 각 상대 노드의 `STOP_ACK`가 없으면 그 노드에만 다시 보냅니다.

상대 ESP32는 paired STM32에서 local `STOP_ACK`를 받은 뒤 Mesh `STOP_ACK`를 보냅니다. 따라서 ACK는
상대 STM32 애플리케이션이 요청을 받아들였다는 뜻이지, 소리나 화면 출력이 끝났다는 뜻은 아닙니다.
낙상도 별도 FALL 메시지를 만들지 않고 `STOP_REQUEST(reason=FALL)`로 통합합니다.

### Q11. 동적 메모리를 사용하지 않는 이유는 무엇인가요?

**한 줄 답변:** 메모리가 제한된 MCU에서 실행 시간과 메모리 사용을 예측하기 쉽게 만들기 위해서입니다.

공통 프로토콜은 고정 크기 버퍼와 큐를 사용합니다. 메모리 단편화 위험은 줄지만, 최대 프레임 크기와
동시 보관 가능한 메시지 수가 고정된다는 한계가 있습니다.

### Q12. 현재 실제로 장착된 장치는 무엇인가요?

**한 줄 답변:** 현재 문서 기준으로 STM32 보드에는 SSD1306과 VS1003B가 장착되어 있고, release-build는
Node 1 기본형, Node 2 DHT11, Node 3 MPU6050 profile을 각각 만듭니다.

배선은 3.3V 로직과 공통 GND를 사용합니다. SSD1306과 MPU6050은 PB8/PB9의 I2C1 버스를 공유하므로
주소와 버스 사용 조건을 함께 관리해야 합니다.

### Q13. 현재까지 구현된 것과 남은 것은 무엇인가요?

**한 줄 답변:** 공통 메시지, UART/Mesh bridge, 센서 상태 기반은 마련되어 있지만 완전한 3노드 실물
시나리오는 아직 검증 중입니다.

남은 핵심 실물 검증 항목은 다음과 같습니다.

- Mesh relay를 포함한 다중 노드 전달 검증
- DHT11·MPU6050 실물 장착 및 노드별 profile의 실제 보드 검증
- XOSS 센서에서 세 dashboard까지 이어지는 종단 간 검증
- 센서 publish, Mesh 전달, 화면·LED·오디오 출력의 통합 검증

### Q14. 전송 성공은 어떤 의미인가요?

**한 줄 답변:** 로컬 전송 함수가 성공했다는 뜻이지, 상대 장치가 메시지를 받고 실제 출력까지
완료했다는 보장은 아닙니다.

전달 보장을 주장하려면 상대 노드의 수신, STM32 application 수락, 출력 결과를 따로 관찰해야 합니다.
`STOP_ACK`는 STM32 application 수락을 의미하며, 오디오나 화면 출력 완료까지 보장하지 않습니다.

### Q15. 다시 개선한다면 무엇을 먼저 하겠습니까?

**한 줄 답변:** 새로운 기능보다 3노드 종단 간 검증을 먼저 완료하겠습니다.

relay와 노드별 센서를 활성화한 뒤 `입력 → publish → Mesh → 수신 → 상태 적용 → 출력` 단계마다
로그와 관찰 기준을 만들겠습니다. 그 다음 패킷 손실, 노드 이탈, 재부팅, 중복 전송 같은 실패
시나리오를 반복 시험하겠습니다.

## 답변할 때 지킬 원칙

1. 결론을 한 문장으로 먼저 말한다.
2. 설계된 기능과 실물로 검증된 기능을 구분한다.
3. 모르는 결과를 추측하지 않고, 어떤 시험으로 확인할지 말한다.
4. `전송 성공`, `수신 성공`, `상태 적용`, `실제 출력 완료`를 같은 의미로 사용하지 않는다.
5. 현재 미구현 항목은 실패가 아니라 다음 검증 단계로 설명한다.
