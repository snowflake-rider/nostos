## 1. 아이디어의 핵심과 합의한 목표

> 센서를 여러 팀원의 보드에 나누어 연결하고, 공통 ESP32 통신 모듈과 Bluetooth Mesh로 데이터를 공유하여 모든 노드가 같은 데이터 항목을 사용하는 대시보드를 제공한다.

브레드보드 공간·배선 제약은 센서 분산으로 줄이고, 공통 인터페이스로 전체 데이터를 함께 사용한다. 각 노드는 자기 센서의 **생산자**이면서 다른 노드 데이터의 **구독자**다.

- Node 1, 2, 3의 기본 ESP32 통신 구성은 유사하며 연결된 센서는 다를 수 있다.
- 센서 배치 확정: Node 1은 속도 센서, Node 2는 온도 센서, Node 3은 MPU6050이다.
- Node 3은 맨 뒤 라이더(Rear Rider)로 확정했다. 기울기·가속도 정보를 이용한 넘어짐 감지 시 자동으로 Mesh 알림 이벤트를 발행하여 앞선 팀원들에게 알리는 것이 목적이다. 센서는 몸과 자전거에 각각 장착해 비교한 뒤 위치를 선택하기로 했다. 최종 고정 위치와 판정 기준은 실험으로 결정한다.
- 팀원에게 공통 C 인터페이스(API)와 통신 모듈을 배포한다. 센서 담당자는 자기 센서의 읽기·해석을 맡는다.
- 노드 사이 데이터 공유는 Bluetooth Mesh를 목표로 한다.
- 이벤트 처리 Task는 주기 작업 Task보다 높은 우선순위를 갖는 방향이다.
- 버튼 메시지 1, 2, 3은 Event이고, 속도는 주기적으로 공유하는 Telemetry다.
- Head의 Bluetooth 속도 센서는 Head ESP32가 읽고, 최근 정상 측정 5개의 이동평균만 공유한다. 다른 노드에서 다시 평균을 내지 않는다.
- 내 보드에 센서가 없어도 다른 노드의 유효한 값은 사용할 수 있다. 아직 받지 못했거나 만료됐을 때는 유효하지 않은 상태로 표시한다.

기존 Head → B → C 속도 전달은 전체 구조의 한 데이터 경로다. Head를 모든 센서 데이터가 반드시 거쳐야 하는 중앙 서버로 확정한 것은 아니다.

## 2. 노드 구성과 데이터 흐름

사용자가 확정한 센서 배치는 다음과 같다. 속도·온도 센서의 제품명과 Node 2/3의 실제 연결 경로는 아직 미정이다. MPU6050의 주요 용도는 넘어짐 자동 알림으로 정했으며, 기울기·가속도 수치 자체도 주기적으로 공유할지는 별도 결정한다.

| 노드 | 연결된 센서 | 자신이 발행하는 것 | 함께 사용하는 것 |
| --- | --- | --- | --- |
| Node 1 / Head | 속도 센서 — 기존 계획은 Bluetooth 연결 | Head의 최근 5개 속도 평균 | Head 속도, Node 2 온도, Node 3 넘어짐 알림 |
| Node 2 | 온도 센서 | 온도값 — 단위·필터·주기는 미정 | 동일한 공유 데이터 항목 |
| Node 3 / 맨 뒤 라이더 | MPU6050 | 넘어짐 감지 시 앞선 팀원들에게 자동 Event 발행. 원시 수치의 주기 공유는 미정 | 동일한 공유 데이터 항목 |

버튼 모듈은 위 센서 배치와 별도다. 버튼이 어느 노드에 있는지, 모든 노드에 하나씩 있는지는 아직 정하지 않았다. 이전 예시의 “Node 2 = 버튼 모듈” 배치는 확정 사항이 아니며 이 표로 대체한다.

```text
로컬 센서 → 센서 Adapter → 공통 통신 인터페이스 → Mesh 발행
                                                   ↓
다른 노드의 Mesh 수신 → 검증·출처 확인 → Telemetry 최신값 / Event 처리
                                                   ↓
                                       대시보드용 조회 인터페이스
```

자기 측정값도 로컬 저장소에 반영한다. 자기 발행 메시지가 무선으로 되돌아와야 자기 화면을 갱신할 수 있는 구조는 피한다.

Mesh의 Model publication/subscription을 이용해 데이터를 배포할 수 있다. 하지만 Mesh 자체가 모든 애플리케이션 저장소를 동일하게 유지하는 분산 데이터베이스는 아니다. 공유 데이터 갱신 규칙은 우리 모듈의 책임으로 설계한다. [ESP-BLE-MESH Model 문서](https://docs.espressif.com/projects/esp-idf/en/v5.0.4/esp32s3/api-reference/bluetooth/esp-ble-mesh.html)

공통 배포 대상은 메시지 의미·단위, 이벤트/주기 정책, 공유값 조회, 오류·만료 처리다. 노드 식별자, 장착 센서 목록, 발행 항목, 센서별 주기는 설정으로 분리한다. 센서와 화면 연결 방식은 Adapter로 분리한다.

같은 소스와 인터페이스를 재사용하는 것이 목표다. 보드·드라이버 차이가 있어도 동일한 바이너리 하나를 그대로 Flash할 수 있다는 뜻은 아니다. 실제 대시보드 표시 장치도 아직 미정이다.

## 3. “같은 데이터”와 SharedState

목표는 같은 데이터 키와 의미를 사용하는 것이다. 모든 화면이 매 순간 동시에 바뀌는 강한 동기화를 뜻하지 않는다. 공유 데이터는 하나의 논리적 모델이지만, 저장 공간은 각 노드에 따로 존재한다.

연결이 유지되고 최신 상태가 계속 전달되는 조건에서 값이 따라잡는 구조를 지향한다. 단절 중에는 노드별 값이 다를 수 있다. 재참여 시 최신 상태를 다시 얻는 절차가 없으면 자동으로 값이 같아진다고 보장할 수 없다.

### 필요한 정보 — 리뷰 제안

| 정보 | 필요한 이유 |
| --- | --- |
| source node + sensor instance | 누구의 어느 센서인지 구별하고 같은 종류 센서끼리 덮어쓰지 않는다. |
| 데이터 종류·단위·형식 버전 | 속도·거리 등을 올바르게 해석하고 규약 불일치를 발견한다. |
| 값과 유효성 | 정상 측정된 0과 결측/오류를 구분한다. |
| 측정 버전·재시작 구분 정보 | 중복·역순 업데이트와 송신 노드 재부팅을 처리한다. |
| 수신 노드의 관측 시각·만료 정책 | 오래된 값을 최신처럼 계속 표시하지 않는다. |

이 표는 논리 정보다. 전부를 payload에 중복해서 넣으라는 뜻은 아니다. Mesh 송신 주소 등과 연결해 결정한다. 정수 폭, 바이트 배치와 인코딩은 아직 미정이다.

초기에는 한 데이터 키에 한 발행 주체만 두는 것이 단순하다. 다른 노드는 그 값을 자기 측정처럼 덮어쓰거나 새 데이터로 재발행하지 않는다. 원본 측정 주체와 중계 노드는 구분한다.

### 유효성·최신성 규칙 — 리뷰 제안

- UNKNOWN: 받은 값이 없으면 “미수신”으로 표시한다.
- VALID: 정상값과 출처를 함께 표시한다. 속도 0도 정상값이다.
- STALE: 마지막 값을 남겨도 “오래된 값”이라고 표시하며 정상 최신값으로 사용하지 않는다.
- INVALID: 센서 오류 정보를 받았다면 미수신과 구분한다.
- 한 노드가 끊겨도 그 노드가 제공하던 데이터만 만료시킨다. 다른 노드의 정상값까지 지우지 않는다.
- 중복 패킷은 새 측정이 아니다. 같은 측정 버전의 재전송만으로 신선도 타이머를 계속 연장하면 안 된다.
- 노드별 시계는 자동 동기화되지 않는다. 서로 다른 노드의 raw timestamp를 직접 빼지 않는다.
- 수신 시각만으로 원본 측정의 실제 나이를 증명할 수는 없다. 발행자는 만료된 샘플을 정상값으로 발행하지 않아야 한다. 초기 재동기화에 측정 경과 시간 정보가 필요한지도 결정한다.

이 네 상태는 앞으로의 데이터 모델 제안이다. 현재 코드에 해당 enum이 구현되어 있다는 뜻은 아니다.

## 4. Event와 Telemetry의 차이

| 구분 | Event: 버튼·넘어짐 알림 | Telemetry: 속도·온도 등 |
| --- | --- | --- |
| 의미 | 사건이 발생했다 | 현재 측정 상태가 이렇다 |
| 보관 | 개별 사건을 큐에 보관 | 데이터 키별 최신값 보관 |
| 중복 판단 | 같은 코드라도 다른 클릭이면 별도 사건 | 같은 측정의 재전송이면 중복 업데이트 |
| 밀렸을 때 | 용량 초과·손실을 명시적으로 처리 | 과거 송신 대기값 대신 최신 상태 선택 |
| 수신 후 | 이벤트 처리기, 필요하면 화면 이력 갱신 | SharedState 갱신 후 화면 조회 |

수신 이벤트 중복 실행을 막으려면 사건 식별 정보가 필요하다. 재시도에서도 같은 사건 식별자를 유지해야 한다. 버튼 1을 두 번 눌렀다고 두 번째 클릭을 중복으로 버리면 안 된다.

버튼 전달 보장 수준은 아직 미정이다. 로컬 큐 접수, Bluetooth 전송부 접수, 상대 애플리케이션 처리 완료는 다르다. 현재 bool 전송 콜백은 상대 수신 ACK나 정확히 한 번 실행을 보장하지 않는다.

속도의 5개 이동평균은 Head에서만 수행한다. 수신 평균을 새 원시 샘플로 취급하지 않는다. 다른 센서에 같은 필터를 일괄 적용하지 않고 담당자가 의미와 허용 지연을 정한다.

### Node 3 / 맨 뒤 라이더의 넘어짐 자동 알림 — 목적 확정, 상세 규칙 미정

```text
MPU6050 측정 → 센서 담당 코드의 기울기 추정·넘어짐 판정
             → 넘어짐 이벤트 생성 → 높은 우선순위의 통신 처리
             → Mesh 그룹 발행 → 앞선 Node 1/2에서 수신 후 알림 처리
```

MPU6050은 가속도와 각속도를 측정하는 장치다. 센서 자체가 “사람이 넘어졌다”는 확정 메시지를 Bluetooth로 발행하는 것은 아니다. 기울기 추정·넘어짐 판정은 센서 담당 코드, 사건 접수·전송은 통신 모듈의 책임으로 나눈다. [TDK MPU-6000/MPU-6050 제품 사양](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Datasheet.pdf)

여기서 사용자의 broadcasting은 팀원에게 알림을 공유한다는 의미다. 현재 표준 Mesh 목표에서는 알림 그룹을 구독한 노드로 발행하는 방식으로 구체화한다. 일반 BLE Advertising을 모든 근처 스마트폰이 알림으로 받는다는 뜻은 아니다. [ESP-BLE-MESH 그룹 알림 예시](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32/api-guides/esp-ble-mesh/ble-mesh-faq.html)

- 감지된 사건은 속도·온도의 다음 발행 주기를 기다리지 않고 전송 처리를 깨운다. 이는 즉시 전송 요청 목표이지 무선 전달 시간이나 수신 성공 보장이 아니다.
- 사건에는 출처 노드와 동일 사건을 식별할 정보가 필요하다. `FALL_DETECTED`는 설명용 메시지 이름이며 현재 코드에 추가된 enum/API가 아니다.
- 현재 이벤트 API는 버튼 코드 1, 2, 3만 받는다. 넘어짐 알림을 임의의 버튼 코드로 바꿔 넣지 않고 이벤트 종류와 오류·용량 정책을 확장해야 한다.
- 하나의 넘어짐 상태가 지속된다고 매 센서 샘플마다 새 사건을 만들지 않는다. 재전송은 같은 사건으로 식별하고, 새로운 넘어짐을 판정하는 재무장 조건을 따로 정한다.
- 판정 임계값·지속 시간·부착 방향·충격과 정상 움직임의 구별은 아직 정하지 않았다. 장착 위치에 맞춰 오탐과 미탐을 함께 시험해야 한다.
- 넘어짐 알림과 버튼 사이의 상대 우선순위, 큐가 가득 찼을 때의 긴급 이벤트 접수 정책, 수신 확인·재시도 범위는 미정이다.
- 화면/부저 등 알림 방식, 알림 유지·해제·취소 규칙도 미정이다. 재참여 노드에 현재 상태를 알려주는 것과 과거 사건을 다시 실행하는 것을 구분한다.

넘어짐 알림의 대상은 맨 뒤 라이더로 정했다. 몸과 자전거 양쪽 장착을 시험하고 결과를 비교해 선택한다. 현재는 어느 한쪽으로 확정하지 않으며, 부착 위치가 미정이라는 이유로 통신 인터페이스 설계를 중단하지 않는다. Node 1/2 자신의 넘어짐까지 이 센서 한 개로 감지하는 것은 아니다.

역할상 Head는 속도를 뒤쪽 팀원들과 공유하고, Rear Rider는 넘어짐 알림을 앞쪽 팀원들과 공유한다. 이는 데이터의 생산자와 수신 대상을 설명한 것이며, 무선 패킷 경로를 반드시 1 → 2 → 3 또는 3 → 2 → 1로 고정한다는 뜻은 아니다.

### 부착 위치 비교 실험

몸/자전거 양쪽을 시험한 뒤 선택하는 진행 방식은 사용자와 합의했다. 아래 비교 기준은 리뷰 제안이며 아직 실험 결과는 없다.

- 오탐: 정상 움직임이나 진동을 넘어짐으로 잘못 알리는지 확인한다.
- 미탐·판정 지연: 넘어짐 모사 상황을 놓치는지, 판정까지 얼마나 걸리는지 기록한다. Mesh 전달 시간은 별도로 측정한다.
- 장착 조건: 위치·방향·고정 방식과 사용한 판정 설정을 함께 기록해 비교한다.
- 사용성: 장착 안정성, 착용·설치 편의성을 비교한다.
- 안전한 시험 장치와 기록 데이터를 사용하며, 사람이 실제로 넘어지는 시험을 전제로 하지 않는다.

장착 위치에 따라 달라지는 측정·판정은 센서 담당 코드에서 다루고, 통신 모듈은 공통 넘어짐 이벤트를 받는 구조로 설계한다. 전용 이벤트 형식과 수신 처리는 시험용 사건 입력으로 먼저 개발·검증할 수 있다. 이 검증을 실제 센서의 넘어짐 감지 성능으로 간주하지 않는다.

## 5. Task priority와 상태 소유권

“ESP32 통신 최우선”은 각 보드에서 통신·긴급 이벤트에 충분한 실행 기회를 주겠다는 정책이다. 칩 자체의 우선순위나 서로 다른 MCU 사이의 공통 RTOS 스케줄러를 뜻하지 않는다.

Task priority는 CPU 실행에 관한 것이다. 무선 송신 대기열 순서나 모든 노드의 수신 순서를 보장하지 않는다. ESP32-S3 멀티코어에서는 두 Task가 동시에 실행될 수도 있다. [ESP-IDF SMP scheduling](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/freertos_idf.html#smp-scheduler)

높은 우선순위 Task도 ESP-IDF Bluetooth 시스템 Task를 굶기면 안 된다. 일이 없으면 큐/알림에서 blocking하고, 짧게 처리한 뒤 대기한다. 우선순위 숫자는 실제 SDK 설정과 측정 결과로 결정한다. [ESP-IDF Task priorities](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32s3/api-guides/performance/speed.html#task-priorities), [FreeRTOS Queue](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/02-Queues-mutexes-and-semaphores/01-Queues)

이벤트가 계속 유입되어 높은 Task가 항상 Ready라면 낮은 Task는 계속 밀릴 수 있다. 현재 burst 한도는 메시지 선택 규칙이지 CPU 점유 한도가 아니다. RTOS 통합에서는 처리 시간 예산과 과부하 정책도 정하고, 높은 Task에 일이 계속 있는 조건으로 시험해야 한다.

**주기 작업이라고 모두 덜 중요한 것은 아니다.** MPU6050의 연속 측정·넘어짐 판정에는 자체 지연 요구가 있다. 온도 표시용 저우선순위 주기 작업과 무조건 묶지 않는다. 센서 측정/판정의 실행 기회와, 판정 후 Event 전송 우선순위를 별도로 설계해야 한다.

### 두 애플리케이션 Task를 유지하는 후보 — 리뷰 제안

| Task | 상대 우선순위 | 책임 |
| --- | --- | --- |
| Event/Comm Task | 높음 | 버튼·수신 메시지 처리, 공통 통신 상태 소유, 전송 순서 조정 |
| Periodic Task | 낮음 | 주기 작업·센서 측정 요청/결과 전달. 공통 상태는 직접 수정하지 않음 |

모든 comm 상태 변경을 Event/Comm Task 한 곳으로 모으는 후보안이다. Periodic Task와 BLE/UART callback은 RTOS-safe 큐/알림으로 작업을 전달한다. 화면에는 일관된 읽기용 snapshot을 제공한다. 현재 구현에는 이 RTOS 전달 계층과 snapshot 인터페이스가 없다.

Event/Comm Task는 버튼 외에도 수신 메시지·주기 마감·전송 재시도 시점에 깨어날 수 있어야 한다. 버튼 큐만 무기한 기다리면 속도 전송이 멈춘다. 센서 읽기나 느린 화면 출력을 높은 우선순위 Task 안에서 기다리지 않는다.

두 Task를 이벤트 전용과 주기 작업 전용으로 완전히 분리하고 송신 전용 Task까지 두면 애플리케이션 Task는 세 개다. Bluetooth 등 시스템 Task는 별도로 존재한다. 정확한 분할은 구현 전에 결정한다.

현재 [comm.h](../../../experiments/communication-module/service/comm.h)는 단일 실행 흐름용이다. 같은 comm 상태를 두 Task에서 동시에 호출하거나 두 코어에 각각 배치하는 것만으로 안전해지지 않는다.

## 6. 현재 구현과 필요한 확장

아래 표는 2026-08-27 설계 리뷰 당시의 구현과 확장 경계를 보존한 것이다. 이후 진행 결과는 [STATUS](STATUS.md)에 기록한다. [구현 현황](../../../experiments/communication-module/README.md)과 [현재 송신 계약](../../../experiments/communication-module/service/README.md)을 함께 본다.

| 항목 | 현재 상태 | 필요한 확장 |
| --- | --- | --- |
| 메시지 | 버튼·Head 속도의 내부 C 자료형 | 출처·센서 식별·버전·wire encoding |
| 송신 | Event FIFO, 평균, 주기, BUSY, burst 한도 | 여러 Telemetry 키의 주기·공정성·용량 정책 |
| 속도 조회 | Head의 로컬 평균 | 로컬·원격 공유 데이터 조회 |
| 동시성 | 단일 실행 흐름 | RTOS 입력 전달과 상태 소유권 |
| 수신·SharedState | 미구현 | 중복·역순·재부팅·만료·복구 처리 |
| 실제 통신·화면 | 이 모듈에 미연결 | UART, BLE 센서, Mesh Model, 화면 Adapter |

센서마다 Task를 하나씩 추가하는 것이 기본 해법은 아니다. 먼저 데이터별 주기와 짧은 작업을 관리하고 블로킹 특성·지연 요구가 다른 작업만 분리를 검토한다.

표준 Mesh Relay는 네트워크 계층에서 수행되며 수신 애플리케이션의 저장·표시와 다르다. 수신할 때마다 새 메시지로 재발행하지 않는다. 기존 custom Advertising 학습 결과를 표준 Mesh 공유 데이터 완료로 간주하지 않는다. [ESP-BLE-MESH Architecture](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/esp-ble-mesh/ble-mesh-architecture.html)

## 7. 아이디어 리뷰

### 종합 의견

**팀 프로젝트의 분산 센서 통합 프로토타입으로 진행할 가치가 있다.** 공간 제약을 줄이고 팀원의 작업을 분리하면서 공통 인터페이스를 실제로 사용할 이유가 분명하다.

핵심 난점은 Task 두 개를 만드는 일이 아니라 **공유값의 의미·출처·수명과 수신 상태를 일관되게 관리하는 것**이다. 전달 성공만으로 대시보드가 신뢰할 수 있는 최신 상태를 갖는 것은 아니다.

### 장점

1. 브레드보드 배선·GPIO·실장 부담을 노드별로 나눌 수 있다.
2. 팀원이 센서 Adapter를 독립 개발하고 동일한 인터페이스로 통합할 수 있다.
3. 센서가 없는 노드에서도 원격 정보를 활용하는 명확한 시연이 가능하다.
4. 출처·만료·단절 같은 분산 시스템 문제를 작고 검증 가능한 범위에서 배울 수 있다.

### 주요 위험과 권장 대응

| 중요도 | 위험 | 권장 대응 |
| --- | --- | --- |
| 높음 | 다른 사람의 값을 내 측정값처럼 표시 | 출처·측정 대상을 명시하고 Head 속도와 내 속도를 구분한다. |
| 높음 | 단절 후 마지막 값이 최신처럼 남음 | 센서별 만료와 재동기화를 정의하고 상태를 표시한다. |
| 높음 | 두 Task가 공통 큐·평균·저장소를 동시에 수정 | 한 소유 Task와 RTOS-safe 입력 전달을 우선 검토한다. |
| 높음 | 이벤트 폭주로 낮은 우선순위 Task가 실행되지 못함 | 메시지 burst와 별도로 CPU 처리 예산·과부하 정책을 정하고 지속 부하를 시험한다. |
| 높음 | 버튼 누락 또는 재전송에 따른 중복 실행 | 사건 식별, 중복 처리, 큐 초과, ACK/재시도 범위를 합의한다. |
| 높음 | 넘어짐 오탐·미탐 또는 판정 지연 | 센서 부착 대상과 기준을 정하고 정상 동작·넘어짐 모사·부하 상황을 함께 검증한다. |
| 중간 | 센서·노드·발행률 증가에 따른 무선 부하 | 필요한 저속 데이터부터 공유하고 크기·발행률·지연을 측정한다. |
| 중간 | BLE 센서 연결과 Mesh 동시 운용을 가정 | 실제 센서와 SDK에서 공존·재연결·전송률을 별도 검증한다. |
| 중간 | 화면 갱신·로그 출력이 통신 처리를 지연 | 느린 표시 작업을 분리하고 실행 시간을 측정한다. |

**공간을 아끼는 것과 측정 위치를 대체하는 것은 다르다.** Node 3에 장착한 센서의 값은 Node 3에서 측정한 값이다. 공유해도 Node 1 자신의 상태를 측정한 것은 아니다. 제품에서 각 자전거에 필요한 로컬 센서를 공유만으로 제거할 수는 없다. 이는 통신 성능과 별개인 제약이다.

센서를 분산하는 데 Mesh가 반드시 필요한 것은 아니다. 다만 프로젝트의 멀티홉 공유 목표에는 검토 가치가 있다. 세 보드가 모두 직접 통신하는 실험만으로 Relay의 필요성이나 성공을 입증하지 않는다.

## 8. 작은 MVP와 검증 순서 — 리뷰 제안

1. **데이터 사전:** 센서 배치, 데이터 키, 단위, 발행 주체, 유효 기간, 화면 항목을 확정한다.
2. **호스트 공유 상태:** 가짜 Node 1/2/3으로 로컬·원격 갱신, 중복·역순·단절·복구를 시험한다.
3. **wire 규약과 수신 인터페이스:** 버전·길이·지원 데이터 검증을 추가한다. C 구조체 메모리를 그대로 보내지 않는다.
4. **RTOS Adapter:** 상태 소유권과 두 Task 후보를 검증한다. 이벤트 폭주 중에도 주기 데이터와 Bluetooth 시스템 처리가 실행되는지 확인한다.
5. **두 노드 실통신:** Provisioning과 키/Model 설정 후 같은 사용자 데이터가 상대 저장소·화면까지 도달하는지 확인한다.
6. **세 노드 공유·Relay:** 모든 노드의 전체 데이터 항목을 확인한다. 별도의 직접 수신 불가 조건에서 Relay OFF/ON 결과도 비교한다.

기존 Layer 및 표준 Mesh 기본 예제 검증과 병행할 수 있지만 서로의 성공 판정을 자동으로 가져오지 않는다.

### MVP 완료를 판단할 관찰 항목

- 센서 없는 노드에서도 원격 정상값을 출처와 함께 조회한다.
- 정상 측정 0과 미수신·만료를 구분한다.
- 송신 노드 전원 차단 후 만료 표시가 나오고 복귀 후 새 상태로 회복한다.
- 늦게 참여한 노드도 최신 상태를 얻는다. 오래된 클릭 이벤트는 재실행하지 않는다.
- 연속 클릭은 각각 처리하고 같은 사건의 재전송은 중복 실행하지 않는다.
- Node 3에서 시험용 넘어짐 사건을 만들면 주기 발행을 기다리지 않고 그룹 알림을 요청한다. 한 사건의 반복 수신과 새로운 사건을 구분한다.
- 실제 센서 판정은 안전한 시험 장치/기록 데이터로 별도 검증한다. 사람이 실제로 넘어져야만 검증할 수 있는 시험을 전제로 하지 않는다.
- 과거 측정 버전이 최신값을 덮어쓰지 않고 중복 수신이 신선도를 늘리지 않는다.
- 버튼이 몰려도 주기 데이터가 무기한 밀리지 않는다. 허용 지연·부하 수치는 시험 전에 정한다.
- 실제 수신·Relay는 보드별 로그로 증명하며 호스트 테스트나 빌드 성공으로 대체하지 않는다.

이 MVP는 프로토타입 검증이다. 실제 주행 안전 기능의 신뢰성이나 모든 환경에서의 전달 보장을 의미하지 않는다.

## 9. 구현 전에 결정할 사항

1. 확정된 센서 배치의 세부 사항: 속도·온도 센서 제품과 실제 연결 경로를 확인한다. MPU6050 고정 위치·판정 기준은 몸/자전거 비교 실험 후 결정하며 통신 인터페이스 설계의 선행 차단 조건으로 두지 않는다. 원시 수치의 주기 공유와 버튼 배치는 별도 결정.
2. 대시보드가 STM32 화면, 별도 디스플레이, PC/앱 중 무엇인지.
3. 데이터 키·발행 주체 매핑과 Head 변경 시 속도 출처 선택 방식.
4. 센서별 측정 주기·발행 주기·만료 간격·허용 지연.
5. 재참여 시 상태 재요청 또는 주기 snapshot 중 사용할 정책.
6. 측정 버전, 재부팅/session 변경, sequence wraparound 처리 규칙.
7. 버튼·넘어짐 알림의 상대 우선순위와 전달 보장 범위, 큐 초과·ACK·재시도·알림 해제·재무장 정책.
8. 두 Task의 정확한 책임, 상태 소유자, callback 입력 전달 방식.
9. Sensor Model/Vendor Model 선택, 그룹·구독 설정, Provisioner와 키 관리 담당.

초기에는 센서 자동 발견, 발행 주체 자동 선출, 완전 동기화, 무제한 확장까지 한꺼번에 만들지 않는다. 고정된 세 노드와 작은 데이터 목록으로 위 계약부터 검증하는 것을 권장한다.
