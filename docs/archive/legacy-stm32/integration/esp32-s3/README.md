# STM32와 ESP32로 메시지 공유하기

처음에는 이 문서만 읽으면 됩니다.

**STM32가 센서를 읽고, ESP32가 다른 라이더에게 전달합니다.**

코드와 빌드 검사는 끝났습니다. 실제 보드끼리 메시지가 오가는지는 아직 시험하지 않았습니다.

## 1. 누가 무엇을 하나요?

- **STM32**: 버튼·센서를 읽고, 어떤 메시지를 보낼지 결정합니다. 받은 메시지로 LED·음성 등을 처리합니다.
- **ESP32**: STM32의 메시지를 받아 Bluetooth Mesh로 보내고, 다른 라이더의 메시지는 자기 STM32에 전달합니다.

한 라이더에게 STM32와 ESP32가 한 쌍씩 있습니다. 두 보드는 UART라는 유선 통신으로 연결합니다.

```text
라이더 A: STM32 → ESP32
                   ↓ Bluetooth Mesh
라이더 B: STM32 ← ESP32
```

B도 A에게 보낼 수 있습니다. 모든 라이더가 같은 송수신 구조를 사용합니다.

## 2. 예제: A가 “잠깐 멈추자” 버튼을 누르면

1. A의 STM32가 버튼을 읽고 **정지 요청**을 만듭니다.
2. A의 ESP32가 정지 요청을 Mesh로 보냅니다.
3. B의 ESP32가 받으면 B의 STM32로 전달합니다.
4. B의 STM32가 정지 요청에 맞는 알림을 처리합니다.

보낼 때 긴 문장 대신 미리 정한 번호를 사용합니다. 정지 요청의 번호는 `0x13`입니다.

```text
STM32 A → ESP32 A:  13
ESP32 A → ESP32 B:  01 13
ESP32 B → STM32 B:  13
```

위 숫자는 16진수입니다. `01`은 메시지 형식의 버전, `13`은 정지 요청입니다.
즉, ESP32는 메시지의 의미를 바꾸지 않고 전달용 형식만 붙였다가 뗍니다.

이것은 **코드가 의도한 동작 예시**입니다. 실제 무선 수신을 확인한 기록은 아닙니다.

## 3. 메시지가 여러 개 들어오면?

**Queue는 잠깐 기다리는 줄**이라고 생각하면 됩니다.

```text
입력: 정지 요청 → 후방 경고
대기: [정지 요청] [후방 경고]
처리: 먼저 들어온 정지 요청부터 하나씩 전달
```

현재는 두 방향의 메시지를 합쳐 최대 **32개**까지 보관합니다.

- 꽉 차면 새로 들어온 메시지는 버립니다.
- 앱이 받은 뒤 **1초 이상** 지난 메시지는 꺼낼 때 버립니다.
- Mesh 설정이 준비되지 않았다면 UART 메시지를 보관하지 않고 버립니다.
- 다른 라이더에게 받은 메시지는 STM32에 넘깁니다. 앱이 같은 메시지를 새로 만들어 보내지는 않습니다. 무선 중계는 Mesh의 Relay 기능이 맡습니다.

큐 관리는 이미 ESP32 코드에 들어 있습니다. 센서 담당 팀원이 직접 구현할 필요는 없습니다.

## 4. 지금 되는 것과 나중에 붙일 것

지금 만든 것은 **“정지 요청”, “낙차 감지”처럼 어떤 일이 발생했는지 전달하는 기능**입니다.

속도 `23.5 km/h`, 온도 `28°C` 같은 숫자를 주기적으로 공유하는 기능은 다음 단계입니다. 모든 라이더가 같은 대시보드를 보는 기능도 아직 완성된 것은 아닙니다.

## 5. 다음에는 무엇을 확인하나요?

1. **빌드**: 코드를 보드에 넣을 프로그램으로 만듭니다. 여기까지는 확인했습니다.
2. **배선·Flash**: STM32와 ESP32를 연결하고 각 보드에 프로그램을 넣습니다.
3. **Mesh 설정**: ESP32들을 같은 통신 그룹에 등록합니다.
4. **버튼 한 번 시험**: A에서 누른 정지 요청이 B의 STM32에 도착하는지 확인합니다.

처음에는 메시지를 하나씩 보내고, 상대가 받은 것을 확인한 뒤 다음 것을 보냅니다. 현재는 메시지가 몰리면 빠질 수 있고, 보낸 쪽에서 상대의 수신 완료를 확인하는 기능도 없습니다.

배선과 설정은 [상세 참고의 1~3절](DETAILS.md#1-빌드부터)을 따라갑니다. 전원을 끈 상태에서 핀을 확인하고, 기존 Mesh 설정은 임의로 지우지 않습니다.
