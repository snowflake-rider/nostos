### 사용자 확인 사항

- 공유 측정값은 부동소수점 대신 크기가 정해진 정수로 저장·전송합니다. 아래 소수 첫째 자리 예시는 10배 정수로 표현합니다.
- 당사자 보드만 자기 낙상 사건의 해제를 공유합니다. 다른 보드는 자기 소리만 잠시 끄며 공유 사건은 해제하지 않습니다.
- 2026-08-29: 역할은 1~3으로 제한하고 역할별 기능을 사전 정의하므로 `capabilities`를 전송하지 않습니다. 실제 역할별 기능 목록은 후속 결정입니다. 발신자→역할 매핑과 기능표는 모든 보드가 동일하게 가져야 합니다.
- heartbeat 내용은 현재 상태 `status` 1바이트입니다. 센서의 지원 여부와 정상 동작 여부를 구분하며 상태 비트 배치는 아직 미정입니다.
- 온습도 내용은 2바이트: 온도 22.5~47.5°C를 0.1°C 간격, 습도 0~100%를 0.5%p 간격으로 표현합니다. 습도 반올림 손실을 허용합니다. 범위 밖/오류는 별도 코드로 표시하고 정확한 범위 밖 값은 이 형식으로 복원하지 못합니다.

## 1. 무엇을 만들까?

현재는 주로 “정지 요청” 같은 명령 번호를 전달합니다. 앞으로는 **누가 보냈는지, 어떤 값인지, 얼마나 최신인지, 어느 낙상 사건인지**도 전달하려고 합니다.

초기 가정은 자전거 3대가 자기 센서값과 경고를 공유하고, 각 STM32가 자기 OLED·LED·부저·음성을 제어하는 것입니다. 속도값의 생산자와 표시 대상은 아직 정하지 않았습니다.

```mermaid
flowchart LR
    A["자전거 A STM32\n센서·판정·화면·알림"] <-->|UART| EA["A ESP32\n메시지 전달"]
    EA <-->|Bluetooth Mesh| EB["B ESP32\n메시지 전달"]
    EB <-->|UART| B["자전거 B STM32\n상태 저장·화면·알림"]
```

C도 같은 구조로 참여합니다. 그림은 제안하는 데이터 흐름이며 실물 전달 성공을 뜻하지 않습니다.

**전부 다시 만들지는 않습니다.** 기존 핀·센서 드라이버·출력 코드·ESP32 Layer 8 기반을 보존하고, 공통 codec과 수신 처리·상태 관리를 확장합니다. ESP32가 센서 판정이나 낙상 해제 권한을 대신 결정하지 않습니다.

## 2. 무엇을 보내고, 무엇은 보내지 않을까?

| 기능 | 보내려는 메시지 | STM32 안에서 처리할 일 |
| --- | --- | --- |
| 버튼 요청 | 정지·감속·가속·주의 요청, 발생 장치와 메시지 식별 | 버튼 판독, 받은 요청의 출력 |
| OLED | 화면 픽셀 대신 아래의 값·상태 | 각 보드가 화면을 그림. 화면 갱신 주기와 무선 전송 주기는 별개 |
| DHT11 | 온도·습도·측정 유효성·새 측정인지 구분할 정보 | 센서 읽기, 미수신·센서 오류·오래된 값 표시 |
| 속도 | 속도·측정 유효성·출처 | 공급 경로는 미정. 정지한 0 km/h와 측정 불가를 구분 |
| 보드 역할 | 기능 목록은 전송하지 않음. 발신자별 역할과 역할별 기능표를 사전 공유 | 역할 1~3만 사용. 장착 기능과 현재 센서 오류를 구분 |
| 낙상 | 발생 장치·사건 식별·활성/해제 상태 | 의심·카운트다운·취소·재감지 판정, 노드별 경고 보관 |
| 연결 상태 | 로컬 UART 상태와 원격 장치 상태를 구분한 heartbeat | 통신 끊김 표시. 오래된 측정값을 새 값으로 바꾸지 않음 |

정수 저장·전송 방침은 사용자가 확인했습니다. 로컬 물리량은 온도 `362 = 36.2°C`, 습도 `605 = 60.5%`, 속도 `237 = 23.7 km/h`처럼 10배 정수로 보관하는 안입니다. 온습도 전송은 별도의 1바이트 코드 두 개로 줄이며, 습도 입력 60.3%는 공유 시 60.5%로 반올림됩니다. 정확한 오류 코드·속도 단위/범위는 후속 결정입니다. C 구조체나 float의 메모리를 그대로 보내지 않습니다.

원본의 주기(화면 200ms, DHT11 1200ms 등)는 참고값이며 NOSTOS의 확정값이 아닙니다. 기존 센서 기본값도 이 초안 때문에 바꾸지 않습니다.

## 3. 메시지 형식의 방향

**추천: 공통 메시지 의미 + UART와 Mesh 각각의 전송 형식.**

| 접근 | 장점 | 비용 |
| --- | --- | --- |
| 공통 메시지를 정의하고 UART에만 경계·길이·CRC를 추가 | 무선으로 불필요한 UART 포장까지 보내지 않음 | ESP32에 포장·해제 과정 필요 |
| UART 패킷 전체를 Mesh에 그대로 넣기 | 같은 묶음을 그대로 운반하기 쉬움 | 시작 표식·CRC 등도 무선으로 보내므로 길이와 분할 부담 증가 |

개념적으로 필요한 정보는 다음과 같습니다. **아래 항목이 모두 모든 패킷의 고정 헤더가 된다는 뜻은 아닙니다.**

| 정보 | 쉬운 의미 |
| --- | --- |
| 규격 버전 | 어떤 약속으로 읽어야 하는가 |
| 발신 장치 | A·B·C 중 누구의 값/사건인가 |
| 메시지 종류와 내용 | 온습도인지 정지 요청인지, 실제 값은 무엇인가 |
| 메시지 식별·순번 | 같은 메시지가 다시 왔는지, 어떤 상태가 더 최신인지 |
| 재시작 구분 | 전원을 껐다 켜서 순번이 다시 시작된 것인지 |
| 낙상 사건 식별 | 어느 낙상 한 건에 대한 시작/해제인가 |
| UART 길이·CRC | 묶음이 완성됐는지, 전송 중 바이트 오류가 있는지 |

예: **“B의 온도는 36.2°C, 습도는 60.5%로 양자화한 값, 측정 성공”**. 원래 습도 입력이 60.3%여도 합의한 간격으로 변환해 보냅니다. ESP32는 전송 코드를 보존해 전달하고, 받는 STM32는 B의 값만 갱신합니다.

바이트 수·순서·CRC 종류·메시지 번호는 다음 설계 단계에서 정합니다. 기존 8종 명령의 의미와 번호는 가능한 한 보존하되, 새 wire 형식과 구형 형식은 엄격히 구분해야 합니다.

일반 비분할 Vendor Mesh 메시지는 opcode를 제외한 헤더와 데이터 합계가 **8바이트**입니다. 초과가 금지되는 것은 아니지만 분할 전송의 비용을 검토해야 합니다. UART 패킷을 통째로 무선에 넣지 않자는 제안은 이 예산도 고려한 것입니다. [ESP-IDF v5.5.5 FAQ §2.8](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/api-guides/esp-ble-mesh/ble-mesh-faq.html#how-many-bytes-can-be-carried-when-sending-unsegmented-messages)

## 4. 바이트 배치보다 먼저 정할 동작 규칙

- **완성된 패킷만 실행:** UART 버전·종류·길이·CRC를 검사하고, 불완전/초과/오류/시간초과 패킷은 버립니다. 다음 정상 경계를 찾는 절차를 정의합니다. 실패한 패킷의 `0x13`을 구형 정지 요청으로 다시 해석하지 않습니다.
- **출처 보존:** Mesh에서 받은 주소와 등록된 논리 장치 ID를 대조하고 STM32까지 출처를 전달합니다. A가 환경 역할이라고 해서 ID 자체를 “환경 역할”과 같은 값으로 고정하지 않습니다.
- **중복과 순서 분리:** 같은 요청의 재전송은 소리를 매번 새로 재생하지 않도록 합니다. 먼저 도착한 온습도 순번이 더 크다는 이유로 늦게 온 낙상까지 버리지 않습니다. 전송 중복과 사건 상태의 최신성은 별도로 판단합니다.
- **낙상은 장치별·사건별:** A의 사건① 해제가 늦게 와도 사건②를 지우지 않습니다. 끝난 사건의 기억도 일정 범위에서 유지하여 지연된 시작 메시지로 되살아나지 않게 합니다. A의 해제가 B의 낙상이나 별도의 SOS를 지우지 않습니다.
- **해제 권한 합의:** 당사자 보드만 자기 사건의 해제를 공유합니다. 다른 보드 버튼은 자기 소리만 잠시 끄고 공유된 사건 상태는 지우지 않습니다. 상대의 발신 주소와 등록된 장치 ID, 해제 대상 사건을 함께 확인해야 합니다.
- **통신 끊김은 정상 복귀가 아님:** heartbeat가 끊기면 “연결 불명”입니다. 상대 장치의 재부팅을 관측해도 기존 경고를 자동 해제하지 않습니다. 경고를 보관하는 수신기 자체가 재부팅했을 때의 복구 방식은 별도로 정해야 하며, Flash 영속 보존을 이미 구현했다는 뜻은 아닙니다.
- **재시작 절차 필요:** 다른 부팅 ID가 왔다는 사실만으로 새 세션이라고 믿으면 안 됩니다. 구세션 지연 패킷을 막을 단조 부팅 번호 또는 명시적 세션 동기화 중 하나를 구현 전에 결정합니다. 순번 넘침·캐시 수명도 함께 정합니다.
- **측정값과 연결 상태 분리:** UART heartbeat는 붙어 있는 ESP32의 응답이지 원격 자전거/센서 전체 정상의 증거가 아닙니다. heartbeat·캐시 재전송은 측정 시각을 새로 만들지 않습니다. 다른 장치의 tick을 내 tick과 직접 빼지 않습니다.
- **유실과 혼잡 대응:** 센서값은 오래된 대기값 대신 최신값을 남기고, 긴급 사건을 우선 처리합니다. 낙상 상태는 변화 때 즉시 보내고 주기 보고로 유실 뒤 복구 기회를 만듭니다. 전송량·재시도·큐는 모두 상한을 둡니다.

CRC는 바이트 오류 검사이며 발신자 인증이 아닙니다. 위 출처 대조도 등록 오류를 줄이는 규칙이며, 키를 가진 악성 노드까지 방어하는 새 보안 설계를 완료했다는 뜻이 아닙니다.

## 5. 어디까지 “전달 성공”이라고 할까?

`UART 송신 완료 → ESP32 접수 → Mesh 송신 요청 성공 → 상대 STM32 상태 반영`은 서로 다른 단계입니다.

현재 사용하는 Mesh server 송신 API는 응용 메시지에 대한 응답을 자동 보장하지 않습니다. 따라서 화면이나 로그에 송신 성공만으로 “모두 전달됨”을 표시하지 않습니다. [ESP-IDF v5.5.5 FAQ §2.5](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/api-guides/esp-ble-mesh/ble-mesh-faq.html#how-to-send-unacknowledged-messages)

첫 버전은 그룹 메시지마다 모두가 ACK(수신 확인 응답)를 보내기보다, 상태 재보고와 중복 억제로 단순하게 시작하는 안을 제안합니다. **모든 상대의 처리 보장이 필요하다면 이 선택을 다시 검토해야 합니다.** ACK를 추가할 때는 대상 상대와 “무엇까지 처리했는지”를 정하고 응답 폭주·무한 재시도를 막습니다.

## 6. 구현으로 넘어갈 때의 단계와 검사

1. **행동 합의:** 속도 생산자, 공유 범위, 낙상 해제 권한, 필요한 전달 확인 수준을 정합니다.
2. **공통 codec:** `libs/protocol/`에서 형식·범위·최대 크기·예제 바이트를 정하고 양쪽이 같은 구현을 사용합니다. USB 로그는 데이터 UART와 분리하고 기존 UART 송신 소유권을 유지합니다.
3. **상태와 기능 연결:** STM32의 장치별 저장소에 습도·유효성·freshness를 추가하고, 링크/낙상 사건 상태는 별도로 관리합니다. OLED는 저장소를 읽습니다. 낙상·센서 판정은 계속 STM32가 맡습니다.
4. **격리 전환:** 구형/신형 UART 자동 감지는 하지 않습니다. 구형 상대가 연결된 채 신형 데이터를 보내지 않도록 시험 구성을 분리하고, STM32–ESP32를 명시적으로 짝지어 바꿉니다. Mesh도 새 버전/메시지 구분자를 정합니다. 실제 Flash는 별도 승인 후 수행합니다.

구현 후 검사할 항목:

- 모든 메시지의 정상/잘못된 길이·종류·버전·CRC, 중간 byte 손실·추가·잘림 후 재동기화.
- 새 데이터 안에 기존 이벤트 번호가 들어 있어도 명령으로 오인하지 않음. 구형/신형 불일치를 명확히 표시.
- 중복·역순·순번 넘침·재부팅 후 구세션 지연 메시지. 늦은 취소①가 낙상②를 지우지 않음.
- A/B 동시 낙상, A만 해제, 별도 SOS 유지. heartbeat 손실로 사건이 사라지지 않음.
- 센서 오류와 실제 0 구분, 오래된 캐시가 새 측정값으로 표시되지 않음, 링크 복귀 후 상태 회복.
- 센서 주기 전송으로 큐가 차도 긴급 사건 처리와 오류 기록이 유지됨.
- DHT11 읽기·OLED 갱신·UART 수신을 동시에 시험. 상대 DHT11의 IRQ 차단 구간은 그대로 이식하지 말고 수신 손실 위험 검토.
- `bash tools/test-host.sh`와 영향 타깃 빌드, 이후 별도 승인한 실물 송수신·센서·출력 검증. 호스트 성공은 실물 성공과 구분.

## 7. 아직 결정하지 않은 것

정수 저장·전송, 낙상 해제 권한, 역할 1~3/기능 목록 전송 생략, heartbeat 내용 1바이트, 온습도 내용 2바이트/습도 반올림 허용은 사용자와 확인했습니다. 현재는 구조체와 codec의 구체안을 검토합니다.

속도값을 어디서 만들지, 선두 한 대의 속도인지 각 자전거 속도인지, 세 보드 모두 모든 값을 표시할지, 상대 처리 확인이 꼭 필요한 메시지는 아직 미정입니다. 바이트 배치는 후속 문서에서 구체적으로 제안하지만 최종 규격으로 확정하지 않습니다.
