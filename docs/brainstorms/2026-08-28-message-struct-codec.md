# 1. 이름: 메시지와 저장소를 구분하기

[전체 구상](2026-08-28-message-protocol-extension-brainstorm.md) · [KAF-373](https://linear.app/kafkasnowflake/issue/KAF-373)

후속 검토: [전체 기능에 필요한 공유/로컬 상태와 확장 규칙](2026-08-29-shared-state-feature-review.md). 이 문서는 알려진 메시지의 압축 형식 제안이고, 후속 문서는 저장소 필드와 미지원 메시지 처리·새 type 추가 규칙을 보완합니다.

**정수 저장·전송과 당사자만 낙상 해제를 공유하는 정책은 합의했습니다. 아래 C 타입·바이트 배치는 구체적인 제안이며, 제품 코드에는 아직 적용하지 않았습니다.**

2026-08-29 추가 합의: 역할은 1~3만 사용하고 역할별 기능은 사전 정의합니다. `capabilities`는 전송하지 않습니다. heartbeat 내용은 `status` 1바이트, 온습도 내용은 온도 0.1°C·습도 0.5%p 간격의 2바이트로 줄입니다. 이 문서는 이전의 heartbeat 3바이트·온습도 5바이트 제안을 대체합니다. 상태 비트와 오류 코드의 구체적인 배정, 공통 헤더·세션 정책은 여전히 제안입니다.

| 이름 | 의미 | 통째로 전송? |
| --- | --- | --- |
| `nostos_message_t` | 지금 보내거나 받은 메시지 한 건 | encoder로 바이트 배열을 만듦 |
| `nostos_node_state_t` | 자전거 한 대의 최신 값·수신 시각·연결·사건 상태 | 아니요 |
| `nostos_network_state_t` | 여러 자전거의 상태를 모은 로컬 저장소 | 아니요 |

공통 메시지는 UART와 Mesh 양쪽에서 사용하므로 이름을 Mesh에 묶지 않습니다. `shared_data`보다 `message`와 `state`로 용도를 구분하는 편이 읽기 쉽습니다. 실제 선언 위치는 향후 `libs/protocol/nostos_message.h`, codec은 같은 라이브러리의 `.c`를 제안합니다. 이 문서에서 해당 파일을 생성하지 않습니다.

# 2. 구조체의 필드

## 정수 단위: 로컬 값과 전송 코드를 구분

| 로컬 값 필드 | C 타입 제안 | 표현 | wire 표현 |
| --- | --- | --- | --- |
| `temperature_c_x10` | `int16_t` | `362` = 36.2°C | 1바이트 offset 코드 |
| `humidity_pct_x10` | `uint16_t` | 센서 입력 `603` = 60.3%; 공유·수신값 `605` = 60.5% | 1바이트, 0.5%p 간격 |
| `speed_kmh_x10` | `uint16_t` | `237` = 23.7 km/h | 2바이트 |

로컬 물리량은 **10배 정수 표현(고정소수점 방식)**을 사용하고, 메시지에는 더 작은 코드를 담습니다. 흔한 32비트 float 2개는 값만 8바이트, 이전 제안의 16비트 정수 2개는 4바이트, 이번 온습도 내용은 오류 표시를 포함해 2바이트입니다. 기준값을 빼기만 하고 정수 타입을 그대로 두면 크기가 줄지 않습니다.

정수값은 메모리 저장과 전송에 모두 사용합니다. 화면에서도 몫과 나머지로 소수 첫째 자리를 출력할 수 있어 float로 되돌릴 필요가 없습니다. 기존 센서 내부의 계산 방식까지 이번 문서에서 변경하지는 않습니다. float로 나온 센서값을 변환한다면 먼저 유효성·범위를 확인하고 10배 후 반올림합니다. 표현 해상도를 높이는 것이 센서 정확도를 높이는 것은 아닙니다.

## 메시지 한 건의 구조 제안

```c
#include <stdint.h>

typedef struct {
    uint8_t temperature_code; /* 0~250: 22.5~47.5°C, 나머지는 아래 상태 코드 */
    uint8_t humidity_code;    /* 0~200: 0~100%, 0.5%p 간격 */
} nostos_environment_t;

typedef struct {
    uint16_t speed_kmh_x10;
    uint8_t  valid;      /* 0: 측정 불가, 1: 유효 */
} nostos_speed_t;

typedef struct {
    uint32_t session_id; /* 사건이 처음 발생한 세션 */
    uint16_t incident_id;
} nostos_incident_ref_t;

typedef struct {
    uint8_t status;       /* 장치 상태 비트. 실제 비트 배치는 후속 결정 */
} nostos_heartbeat_t;

typedef struct {
    uint8_t  version;    /* 제안값 2. 현재 제품의 버전 1과 구분 */
    uint8_t  type;       /* 어떤 union 멤버를 사용할지 결정 */
    uint8_t  source_id;  /* 제안값 1~3. 역할/배열 인덱스/Mesh 주소와 별개 */
    uint32_t session_id; /* 이 메시지를 만든 세션 */
    uint16_t sequence;   /* 같은 메시지 재전송 때는 유지 */
    union {
        nostos_environment_t environment;
        nostos_speed_t       speed;
        nostos_incident_ref_t incident;
        nostos_heartbeat_t   heartbeat;
    } payload;
} nostos_message_t;
```

`union`은 한 메시지가 온습도 또는 속도 또는 사건 정보 중 **하나만** 가진다는 뜻입니다. 정지 요청을 보낼 때 온도·습도까지 매번 보내지 않습니다. 전송 크기는 union 전체의 크기가 아니라 `type`에 해당하는 필드만으로 정합니다.

`session_id`와 `sequence`는 0을 예약값으로 두는 안입니다. 순번이 65535를 넘어가면 조용히 0으로 돌리지 않고 새 세션으로 전환해야 합니다. 재부팅·세션 승인·순환 정책은 codec 밖에서 별도로 구현해야 하며 아직 미구현입니다. 수신 시 낯선 세션을 무조건 최신으로 인정하지 않습니다.

사건 키는 `(source_id, payload.incident.session_id, incident_id)`입니다. 메시지의 현재 세션과 사건 생성 세션을 분리하면 다음 세션에서 이전 사건을 참조할 수 있습니다. 다만 실제 재부팅 뒤 사건 복구·보존 정책까지 해결됐다는 뜻은 아닙니다. FALL과 SOS는 구분해서 관리하며 FALL_CLEAR가 SOS를 해제하지 않습니다.

## 역할과 heartbeat: 합의한 구분

- `role`은 세 라이더의 사전 정의된 역할 1, 2, 3만 허용합니다. 실제 역할별 센서 목록은 아직 이 문서에서 확정하지 않습니다.
- `capabilities`는 “지원·장착한 기능”이지 “지금 센서가 정상인가”가 아닙니다. 역할별 기능표를 모든 보드가 동일하게 가지므로 전송 필드에서 제거합니다.
- `status`는 현재 동작 상태를 알립니다. 센서 오류 등 어느 상태를 어떤 비트로 표현할지는 후속 결정입니다. 장착하지 않은 센서를 고장으로 표시하지 않아야 합니다.
- heartbeat에는 `status`만 넣습니다. 공통 헤더의 `source_id`로 발신자를 식별하고, 미리 등록한 `source_id → role → 기능 목록`을 조회합니다. 역할은 장치 ID나 Mesh 주소와 의미가 다르며, 같은 숫자라고 자동으로 동일시하지 않습니다.
- 역할/기능표와 발신자 매핑을 공통 설정으로 관리해야 합니다. 매핑을 모르면 역할을 추측하지 않고 미등록 상태로 둡니다. 동적인 역할 변경·기능 협상·별도 장치 소개 메시지는 이번 합의에 포함하지 않습니다.

heartbeat 수신은 최근 연락의 증거일 뿐 모든 센서 정상·새 측정·낙상 해제의 증거가 아닙니다. `status`의 최종 비트 배치가 정해지기 전에는 0을 “모두 정상”으로 단정하지 않습니다.

## 저장소에는 무엇을 더 보관할까?

`nostos_node_state_t`에는 위 정수 센서값 외에 **측정별 수신 여부·수신 시각·마지막 측정 식별자**, 로컬/원격 연결 상태, 활성·종료 사건 정보가 필요합니다. `nostos_network_state_t`는 이 노드 상태를 3대분 모읍니다. 상세 런타임 구조는 상태 적용 정책과 함께 다음 단계에서 정의합니다.

온도·습도의 미수신/오류/표현 범위 초과와 실제 0을 구분합니다. 로컬 저장소에는 코드에서 복원한 정수 물리량과 측정별 상태를 별도로 보관하며, 오류 코드를 온도 숫자로 표시하지 않습니다. 로컬 음소거는 별도 UI 상태이며 전송할 낙상 해제 메시지가 아닙니다. 현재 `shared_state_t`의 float 필드는 아직 변경하지 않았습니다.

# 3. Encode: 구조체 → 바이트 배열

**구조체 메모리를 `memcpy`하거나 `sizeof(struct)`만큼 보내지 않습니다.** 구조체에는 정렬용 빈 공간이 들어갈 수 있고, 숫자의 바이트 순서도 약속해야 합니다. `packed`만 붙이는 것도 해법이 아닙니다.

이 제안은 여러 바이트 정수의 **작은 쪽 바이트부터 보내는 Little-endian**을 사용합니다. 온습도는 각각 1바이트 코드이므로 해당 필드 자체에는 endian 차이가 없습니다. 헤더의 세션·순번에는 여전히 바이트 순서 약속이 필요합니다.

## 공통 헤더: 9바이트

| 위치 | 크기 | 내용 |
| --- | --- | --- |
| 0 | 1 | version |
| 1 | 1 | type |
| 2 | 1 | source_id |
| 3~6 | 4 | session_id, little-endian |
| 7~8 | 2 | sequence, little-endian |
| 9 이후 | 종류별 | 해당 payload만 |

payload 길이는 각 메시지 종류에 고정합니다. Mesh 수신 API가 전체 길이를 제공하므로 공통 본문에는 길이를 반복 저장하지 않습니다. UART 바깥 프레임에는 경계 표식·길이·CRC가 필요하며 정확한 framing은 후속 결정입니다.

| 종류/ID 제안 | payload 순서 | payload | 본문 합계 |
| --- | --- | --- | --- |
| 기존 버튼 요청 `0x10~0x13`, 후방 상태 `0x20/0x21` | 없음 | 0 | 9바이트 |
| 속도 `0x40` | valid(1), speed(2) | 3 | 12바이트 |
| 온습도 `0x41` | temperature_code(1), humidity_code(1) | 2 | 11바이트 |
| 낙상 `0x30`, SOS `0x31`, 낙상 해제 `0x42` | 사건 세션(4), 사건 번호(2) | 6 | 15바이트 |
| 장치 heartbeat `0x50` | status(1) | 1 | 10바이트 |

기존 ID의 의미는 보존하지만, 버전 2의 wire는 현재 버전 1과 호환되지 않습니다. 새 ID와 새 Mesh opcode는 최종 승인 전입니다. UART 링크 heartbeat와 원격 노드 heartbeat는 라우팅 범위를 구분해야 하며 아직 이 표만으로 혼용하지 않습니다. ACK도 아직 정의하지 않았습니다.

## 온습도 코드: 계산식과 오류 표시 제안

기준은 송수신 측이 공유하는 고정값입니다. 보드마다 중앙값을 새로 계산하지 않습니다.

| 항목 | 정상 입력 | encode | decode |
| --- | --- | --- | --- |
| 온도 | `temperature_c_x10` 225~475 | `temperature_c_x10 - 350 + 125` → 코드 0~250 | `code - 125 + 350` → 10배 정수 |
| 습도 | `humidity_pct_x10` 0~1000 | `(humidity_pct_x10 + 2) / 5` 정수 나눗셈 → 코드 0~200 | `code * 5` → 10배 정수 |

온도는 35°C를 중심으로 ±12.5°C를 표현합니다. 이는 센서의 측정 가능 범위가 아니라 이번 패킷의 표현 범위입니다. 습도는 중앙값/좁은 범위를 가정하지 않고 전체 0~100%를 표현합니다. 이미 0.1%p 단위인 입력에 위 정수 계산을 적용하면 반올림 오차는 최대 0.2%p입니다. 임의의 실수 원본을 먼저 10배 정수로 만드는 과정의 오차는 별도입니다.

두 코드에 독립적으로 적용할 특수값을 아래처럼 제안합니다. 정상값 밖의 숫자를 이용하므로 `valid_mask`를 추가로 전송하지 않습니다.

| 코드(10진수) | 의미 제안 |
| --- | --- |
| 251 | 표현 범위 미만 |
| 252 | 표현 범위 초과 |
| 253 | 센서 읽기 오류 |
| 254 | 아직 측정 안 됨 / 해당 역할에 센서 없음 |
| 255 | 예약값: 이 규격의 decoder는 거부 |

습도 코드 201~250도 예약값으로 거부합니다. 254의 미측정/센서 없음은 역할별 기능표와 함께 구분합니다. 범위 검사는 **좁은 정수로 cast하거나 반올림하기 전에** 수행합니다. 예를 들어 47.6°C는 온도 코드 252, 22.4°C는 251이며 경계값으로 잘라내거나 정수 넘침을 허용하지 않습니다. 온도 0°C도 이 축소 형식에서는 251이며 정확한 0°C를 복원할 수 없습니다. 넓은 범위의 정확한 값이 필요해지면 별도 형식이 필요하지만 이번에는 구현하지 않습니다.

## 온습도 예제

센서값 36.2°C/60.3%를 정수 362/603으로 받아 코드 137/121로 만듭니다. 수신 측은 362/605로 복원합니다. 습도의 60.3% → 60.5% 양자화 손실은 사용자가 허용했습니다.

```c
nostos_message_t message = {
    .version = 2,
    .type = 0x41,           /* 온습도: 제안 ID */
    .source_id = 2,
    .session_id = 1,
    .sequence = 7,
    .payload.environment = {
        .temperature_code = 137,
        .humidity_code = 121
    }
};
```

11바이트 결과는 다음과 같습니다. 숫자는 16진수입니다.

```text
02 41 02 | 01 00 00 00 | 07 00 | 89 | 79
버전/종류/출처  세션=1       순번=7  온도   습도
```

16비트 값 하나를 쓰는 기본 동작:

```c
static void put_u16_le(uint8_t *out, uint16_t value)
{
    out[0] = (uint8_t)(value & 0xFFu);
    out[1] = (uint8_t)(value >> 8);
}
/* 예: 헤더의 sequence를 쓸 때 사용합니다. */
```

encoder는 먼저 인수·종류별 코드·버퍼 용량을 검사한 뒤 씁니다. 센서 입력을 코드로 만드는 단계와 메시지의 바이트 배열을 만드는 단계는 구분합니다. 정상 코드와 정의된 특수 코드는 허용하고 예약 코드는 거부합니다. 필요한 길이보다 출력 버퍼가 작으면 실패하고 버퍼를 건드리지 않습니다.

# 4. Decode: 바이트 배열 → 구조체

decoder는 아래 순서로 처리합니다.

1. 헤더 9바이트 이상인지 검사합니다. UART라면 먼저 바깥 프레임 경계·길이·CRC 검사를 통과해야 합니다.
2. 버전·종류·출처·세션·순번의 기본 유효성을 검사합니다.
3. 종류에 맞는 **정확한 전체 길이**인지 확인합니다. 온습도는 반드시 11바이트, heartbeat는 10바이트입니다. 이전 초안의 온습도 14바이트를 같은 형식으로 허용하지 않습니다.
4. 바이트를 순서대로 읽고 정상/특수/예약 코드 여부를 확인하여 임시 메시지 구조체에 저장합니다. heartbeat 상태 비트의 검증 규칙은 최종 비트 배치와 함께 정합니다.
5. 모든 검사가 성공한 뒤에만 결과 구조체를 내보냅니다. 실패하면 기존 결과와 공유 상태는 그대로 둡니다.

```c
static uint16_t get_u16_le(const uint8_t *in)
{
    return (uint16_t)((uint16_t)in[0] |
                      (uint16_t)((uint16_t)in[1] << 8));
}
```

예제의 `89`는 코드 137 → 온도 정수 362, `79`는 코드 121 → 습도 정수 605로 복원됩니다. 온도 식 `code - 125 + 350`은 충분히 큰 signed 정수에서 계산하고, 검증 후 결과 타입에 저장합니다. 코드 251~254는 숫자로 복원하지 않고 측정 상태로 처리합니다. 이는 유효한 오류 보고 메시지이며, 패킷 자체가 잘못되어 decoder가 실패하는 경우와 구분합니다.

API 이름은 다음을 제안합니다. 아래는 인터페이스 제안이며 제품 코드에 존재하는 함수가 아닙니다.

아래 bool decoder는 최초의 단순 인터페이스 예시입니다. 후속 확장안에서는 공통 envelope 검사와 type별 해석을 분리하고, `UNSUPPORTED_TYPE`/`UNSUPPORTED_VERSION`과 잘못된 길이/값을 구분하는 결과 enum으로 바꾸는 방향을 제안합니다. 이 API 예시가 최종 계약은 아닙니다.

```c
/* 필요한 길이 반환. 잘못된 메시지이면 0. */
size_t nostos_message_encoded_size(const nostos_message_t *message);

/* 성공 시에만 출력 갱신. written은 실제 쓴 바이트 수. */
bool nostos_message_encode(const nostos_message_t *message,
                          uint8_t *out, size_t capacity, size_t *written);
bool nostos_message_decode(const uint8_t *bytes, size_t length,
                          nostos_message_t *out);
```

실제 헤더에는 `<stdbool.h>`와 `<stddef.h>`도 필요합니다.

**decode 성공과 상태 반영은 다릅니다.** 이후 수신 경로에서 실제 Mesh 발신 주소↔source_id 확인, 승인된 세션, 중복·순서 검사, 사건 소유권 확인을 통과해야 저장소를 갱신합니다. 아무 패킷에나 source_id=2라고 쓰는 것만으로 2번의 해제 권한을 얻는 구조가 아닙니다. CRC 자체도 인증 기능은 아닙니다.

## 전송 크기에 대한 선택

온습도 내용은 이전의 값 4바이트+유효성 1바이트에서 **2바이트**, heartbeat 내용은 3바이트에서 **1바이트**로 줄었습니다. 현재 제안 헤더를 포함하면 각각 **11바이트와 10바이트**입니다. `sizeof(nostos_message_t)`는 패딩과 union 때문에 이 숫자와 다를 수 있습니다. 로컬 물리량 저장소까지 2바이트라는 뜻도 아닙니다.

일반 비분할 Vendor Mesh 본문 한도는 8바이트이므로 **축소 후에도 이 제안의 모든 메시지는 분할 전송 검토 대상**입니다. ESP32 스택의 분할 기능·현재 설정·전송 주기를 검사해야 하며, 온습도 2바이트만으로 비분할 전송이 가능하다고 설명해서는 안 됩니다. 우선 명확한 세션·출처 정보를 보존한 구조로 제안하고, 8바이트 이하가 필수라면 헤더와 세션 전달 방식을 별도 설계합니다. [ESP-IDF v5.5.5 FAQ §2.8](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32s3/api-guides/esp-ble-mesh/ble-mesh-faq.html#how-many-bytes-can-be-carried-when-sending-unsegmented-messages)

## 검증 범위

이전 초안의 14바이트 온습도 예제는 저장소 밖 C probe에서 strict compile·ASan/UBSan·int16 전체 값 왕복 검사 등을 통과했습니다. 이는 **이전 형식의 검증 기록**이며 축소된 새 형식의 구현 검증으로 대체해 인용하지 않습니다.

이번 축소안의 검증 범위는 저장소 밖의 계산·코드 분류 검사와 문서 C 예제 컴파일, 문서 링크·형식 검사입니다. 전체 메시지 codec, UART framing, Mesh 분할 송수신, 역할표 일치 확인, heartbeat 상태 비트, 사건/세션 상태 머신, 보드 실물 동작은 아직 구현·검증하지 않았습니다.

2026-08-29 실제 검사 결과: Python으로 int16 온도 입력 65,536개에 대한 정상 복원/범위 초과 분기, 습도 입력 1,001개에 대한 양자화 오차, 두 코드의 65,536가지 조합에 대한 정상/특수/예약 분류를 확인했습니다. 문서 C 블록과 11바이트 예제를 `cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion -Werror -fsanitize=address,undefined`로 컴파일·실행해 통과했습니다. 이는 독립 예제 검사이며 제품 codec 테스트가 아닙니다. `python3 tools/check_repository.py`, GFM 파싱, 문서 공백·코드펜스 검사도 통과했고 기존 공통 프로토콜·공유 상태 7개 파일의 SHA-256은 동일했습니다.
