# 02. 버튼 없는 UART 단독 시험 — 10/10

검증일: 2026-08-28 (KST).

## 확인하려던 것

버튼 처리와 무관하게 **STM32 PA9에서 보낸 1바이트를 D6 GPIO18이 실제로 받는가?**

기존 STM32 프로젝트의 앱 처리를 임시 우회하고, 기존 `uart_service` 경로로 약 1초마다 `0x13`을 총 10번 송신했다. 새 프로젝트나 IOC는 만들지 않았다. 임시 시험은 10회 뒤 송신을 멈추도록 제한했다.

## 성공한 실행의 조건

1. 사용자가 흰 신호선을 ESP32 GPIO11에서 GPIO18로 이동했다.
2. GPIO18 대기 레벨은 LOW에서 HIGH로 바뀌었다.
3. 이동 직후 첫 실행에서는 수신이 여전히 정체되어 있었다.
4. D6만 재부팅하여 수신 버퍼 0과 기존 Mesh 설정을 확인했다.
5. 이미 설치된 STM32 임시 시험을 reset으로 다시 시작했다.

배선 이동만으로 바로 성공한 것이 아니라, **GPIO18 이동 후 D6 재부팅을 거친 실행에서 성공**했다.

## 실제 결과

| 관찰 지점 | 결과 |
| --- | --- |
| STM32 MCU RAM 송신 시도 | 10 |
| STM32 HAL 송신 성공 / 실패 | 10 / 0 |
| ST-LINK USB 진단 복사본 `0x13` | 10 |
| D6 `UART_RX id=0x13 result=queued` | 10 |

첫 바이트와 마지막 바이트의 실제 로그:

```text
8.341s STM32: USB_TRACE hex=13
8.344s D6: I (27121) LAYER_8_UART: UART_RX id=0x13 result=queued
...
17.304s STM32: USB_TRACE hex=13
17.306s D6: I (36081) LAYER_8_UART: UART_RX id=0x13 result=queued
```

관찰된 STM32 송신 복사본 간격은 약 0.996초였다. 시각은 호스트의 USB 로그 관찰 시각이며, 정밀 UART 파형·지연 측정값이 아니다.

MCU RAM 읽기 결과:

```text
0x20000168 : 0000000A 0000000A 00000000
```

이 임시 이미지에서 순서대로 시도·성공·실패 카운터다. 다른 빌드에서도 같은 RAM 주소가 같은 의미라고 가정하면 안 된다.

## 정상 송신 구간과 reset 구간을 분리

STM32 reset 직후, 첫 시험 바이트 전에 다른 유효 ID 4건, noop 103건, invalid 27건이 관찰됐다. 이를 정상 `0x13` 송신 성공 횟수에 포함하지 않았다.

| D6 카운터 | 첫 시험 바이트 전 | 10회 송신 후 |
| --- | ---: | ---: |
| valid | 4 | 14 |
| noop | 103 | 103 |
| invalid | 27 | 27 |
| hw_errors | 0 | 0 |
| buffered | 0 | 0 |

따라서 **정상 송신 구간의 UART 10/10 전달은 확인**, **reset 구간까지 잡음이 없었다는 주장은 하지 않음**이 정확한 결론이다.

## 이 시험으로 확인하지 않은 것

- 물리 버튼 입력.
- 상대 ESP32의 Mesh 수신. 당시 `MESH_TX accepted`와 경고 로그만으로 상대 수신을 판정하지 않았다.
- 역방향 UART, 장시간 부하, 전원 투입·reset 안정성.

임시 시험 후 원래 STM32 Flash를 복구했다. 이어진 실제 버튼 시험은 [03. 버튼 → Mesh](03-button-to-mesh-test.md), 복구와 남은 문제는 [04](04-recovery-and-limits.md), 원본 위치는 [05](05-evidence.md)에 기록했다.
